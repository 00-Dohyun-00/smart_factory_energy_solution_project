# WATTever 프론트엔드 — CLAUDE.md

프론트엔드(`frontend/`) 작업에만 적용한다.

- 공통 규칙(폴더, 파일 이름, 금지 사항, 커밋)은 루트의 `AGENTS.md`가 기준이다. 이 문서와 다르면 **`AGENTS.md`를 따른다.**
- 코드 예제는 `docs/3-frontend-guide.md`, 기획 원문은 루트의 `WATTever_회의내용정리.md`, 팀 결정은 `docs/decisions.md`를 본다.
- `확인 필요` 표시는 팀에서 아직 정하지 않은 항목이다. 해당 항목에 걸리는 작업은 임의로 정하지 말고 먼저 질문한다.

## 1. 프로젝트 한 줄 요약

공장에 한전 전기 + 태양광 + ESS(배터리)를 함께 공급한다고 가정하고, **15분 최대수요전력(피크) 방어를 최우선**으로 ESS의 충전/방전/대기를 추천해 전기요금을 줄이는 모니터링·운영 추천 시스템이다. 비싼 요금 시간대의 ESS 활용은 차순위 옵션이다.
태양광과 ESS는 가상 설비이고, 데이터는 대부분 시뮬레이션이다. (시연에서는 1번 모터의 실제 값을 일부 결합할 수 있다)

## 2. 기술 스택

| 항목 | 결정 |
|---|---|
| 프레임워크 | Vue 3, Composition API, `<script setup>` |
| 언어 | JavaScript (TypeScript 쓰지 않음) |
| 빌드 | Vite |
| 라우팅 / 상태 | Vue Router / Pinia |
| 차트 | ECharts — 공통 컴포넌트 `@/components/Chart.vue`로만 사용 |
| UI | 라이브러리 없이 직접 작성 (`<style scoped>` + 색 변수) |
| HTTP | `@/api/client.js`의 `api()` 함수 |
| 검사 / 정렬 | oxlint / Prettier |
| 패키지 매니저 | npm |

- Element Plus, vue-echarts, Tailwind 등 `package.json`에 없는 라이브러리는 쓰지 않는다. 필요하면 설치하지 말고 이유와 대안을 먼저 제안한다.
- 수정 금지 공통 파일: `package.json`, `vite.config.js`, `src/api/client.js`, `src/components/Chart.vue`, `src/styles/reset.css`. 꼭 고쳐야 하면 이유를 설명하고 먼저 확인받는다.

## 3. 명령어

```bash
npm install
npm run dev        # http://localhost:5173 (/api 요청은 백엔드 :8080으로 전달됨)
npm run format     # Prettier 자동 정렬
npm run lint       # oxlint
npm run build
```

작업이 끝나면 `npm run format && npm run lint && npm run build`가 통과해야 한다.
환경 변수 파일(`.env`)은 프론트엔드에서 쓰지 않는다.

## 4. 폴더 구조

```
src/
  api/
    client.js          # 공통 호출 함수 api() (수정 금지)
    {기능}Api.js        # 기능별 API 함수 (예: batteryStatusApi.js)
  stores/              # Pinia. use{기능}Store.js
  pages/               # 화면 단위 (주소 1개 = 파일 1개), XxxPage.vue
  components/          # 재사용 UI. Chart.vue(수정 금지), 상태 표시, 지표 카드 등
  layouts/             # MainLayout.vue (헤더 + RouterView)
  router/index.js      # 페이지 목록
  styles/              # reset.css(수정 금지), global.css(색 변수·전체 공통 스타일)
  utils/format.js      # 숫자·단위 표시 함수 (필요해질 때 만든다)
  assets/              # 이미지, factory-layout.svg 등
```

- import는 항상 `@/` 경로, `.vue`는 확장자까지 쓴다.
- 새 폴더나 공통 유틸은 꼭 필요할 때만 만든다. 초보자가 읽을 수 있는 단순한 코드가 우선이다.

## 5. 화면

메뉴는 다섯 개(모니터링 · 분석 · 보고서 · 운영 로그 · 환경 설정)이고, 메뉴 아래에 하위 화면을 둔다. 화면은 한 번에 하나씩 만들어 추가한다. (2026-11-15 결정)

| 메뉴 | 하위 화면 | 경로 | 파일 | 상태 |
|---|---|---|---|---|
| 모니터링 | 통합 | `/` | `MonitoringPage.vue` | 있음 |
| 모니터링 | 설비 모니터링 | `/monitoring/diagram` | `PowerDiagramPage.vue` | 있음 |
| 분석 | 추이 분석 | `/analysis/trend` | `TrendAnalysisPage.vue` | 있음 |
| 분석 | 피크 분석 | `/analysis/peak` | `PeakAnalysisPage.vue` | 있음 |
| 보고서 | 월간 성적표 | `/report` | `ReportPage.vue` | 있음 |
| 운영 로그 | 추천 이력 | `/logs` | `HistoryPage.vue` | 있음 (`/history`로 들어와도 열림) |
| 환경 설정 | 기준값 | `/settings` | `SettingsPage.vue` | 있음 |

- 왼쪽 메뉴(`MainLayout.vue`): 맨 위 `WATTever`, 접었다 펴는 메뉴 5개, 맨 아래 현재 시각·날씨·서버 연결 표시. "통합" 옆에는 지금 피크 단계(■ 경고, ▲ 주의)를 표시한다. 위쪽 헤더는 없다.
- 맨 위 줄 세 개 버튼으로 왼쪽 메뉴 전체를 접었다 편다. 접으면 좁은 띠(56px)만 남고, 띠에는 피크 단계와 연결 상태만 도형으로 보인다. 접은 상태는 브라우저 저장소(`localStorage`)에 적어 두어 새로 고쳐도 유지된다.
- 서버 연결이 끊겼다는 알림은 `MainLayout.vue`가 모든 화면 위쪽에 한 번만 띄운다(마지막 수신 시각, 자동 재연결 안내, `[지금 다시 시도]`). 각 화면에서 따로 만들지 않는다.
- `routes`의 `meta`에 `parent`(메뉴 이름)와 `title`(화면 이름)을 적는다. `title`은 브라우저 탭 제목(`통합 · WATTever`)에 쓰인다. 없는 주소는 왼쪽 메뉴가 보이는 채로 404 안내를 보여 준다.
- 다른 화면으로 옮기면 본문 스크롤을 맨 위로 올린다.
- 새 화면을 만들면 `router/index.js`의 `routes`와 `MainLayout.vue`의 `menus` 두 곳에 추가한다. 아직 없는 화면은 `ComingSoonPage.vue`를 연결하고 `meta`에 메뉴 이름과 제목을 적는다.
- 화면마다 맨 위에 "메뉴 › 화면 이름" 제목 줄을 둔다(`global.css`의 `.crumb`).
- **화면을 새로 만들거나 구성을 크게 바꿀 때는 Figma 시안을 먼저 그려 확인받고 코드로 옮긴다.** 시안 파일: https://www.figma.com/design/T3ZjEgHClEAQC999RJqbMX ("실시간 관제 시안 2" 페이지 아래쪽에 메뉴별 화면이 있다)
- 공장 레이아웃(평면도)은 쓰지 않기로 했다. 설비는 설비 모니터링 화면과 "지금 많이 쓰는 설비" 순위로 보여 준다.
- 회의록의 예시값(공장 2,570kW, 목표 1,800kW 등)은 UI 예시일 뿐 실제 값이 아니다.

### 운영 로그 > 추천 이력 세부

메뉴 이름은 "운영 로그"다(2026-11-16에 "로그"에서 변경). 주소(`/logs`)와 파일 이름(`HistoryPage.vue`)은 그대로 두었다.

- 표 한 줄 = 추천 1건. 열: 추천 시각, 15분 구간, 추천(행동·kW), 근거, 예상 평균, 처리(추천 중/적용/자동/넘김), 처리자·시각, 결과 피크, 결과(목표 이내/목표 초과).
- 줄을 누르면 추천 이유와 판단에 쓴 값(`usedValues`)이 펼쳐진다. 판단 값 목록은 백엔드가 주는 배열을 그대로 그린다.
- 기간(오늘/최근 7일/직접 입력)은 API로 조회하고, 추천·처리·근거·검색어 조건은 받아 온 목록을 화면에서 거른다. 근거 선택 상자의 목록은 받아 온 이력에 나온 `ruleLabel`로 만든다.
- "오늘"은 서버가 보낸 시각(`status.recordedAt`)에서 구한다. 조회 기간에 오늘이 들어 있으면 5초마다 조용히 다시 받는다.
- 이 화면에서는 적용/넘기기를 하지 않는다(읽기 전용). 처리는 모니터링 > 통합에서 한다.
- 자동으로 처리한 기록은 실제 제어가 아니므로 처리자를 "자동 모드 (시뮬레이션)"으로, 처리 조건을 "자동 (시뮬레이션)"으로 적는다.
- 이력용으로 가짜 데이터에 넣은 값(백엔드와 확정 필요): `windowStart`, `windowEnd`, `ruleLabel`, `predictedKw`, `resultPeakKw`, `resultStatus`(`DEFENDED`/`EXCEEDED`).

### 성적표 세부

- 주제는 "한 달 동안 ESS 추천 운영이 실제로 어땠나"이다. 달은 ◀ ▶로 고르고, 이번 달은 오늘까지의 값만 보여 준다. "이번 달"은 서버 시각에서 구한다.
- 구성: 핵심 숫자 4개(피크 방어 성공률, 최대 피크, 평균 피크 저감량, 전기요금 추정) → 일별 최대 피크와 저감량(예상 막대 위에 실제 막대를 겹침) · 피크 시간대 히트맵(날짜 × 시각) / 전기요금 카드(`BillCard.vue`) · 목표를 넘은 구간 표 → ESS 운용 · 태양광·탄소.
- 제목 줄의 `[인쇄 · PDF 저장]`은 브라우저 인쇄 창을 연다(`window.print()`, 라이브러리 없음). 인쇄할 때는 왼쪽 메뉴와 버튼을 숨기고 A4 가로에 맞게 줄인다(`global.css`와 `MainLayout.vue`의 `@media print`).
- 제목 줄의 `[CSV 저장]`은 지금 보고 있는 달의 요약, 일별 최대 피크, 요금 시간대별 값, 목표 초과 구간을 CSV 파일 하나로 내려받는다(라이브러리 없음, 엑셀에서 한글이 깨지지 않게 BOM을 붙임). 숫자는 화면용으로 꾸미지 않고 받은 값 그대로 넣는다.
- 추정값이라는 주의 문구는 화면 맨 아래에 둔다.
- 금액은 백엔드가 원 단위로 주고, 화면에서 만원 단위로 바꿔 보여 준다(`formatManwon`). 요금·저감량·탄소는 모두 추정값이라고 제목 줄에 적는다.
- 피크 저감량은 "방전하지 않았을 때의 예상 피크 − 실제 피크"이고, 두 값 모두 백엔드가 준다.
- 히트맵의 색 단계는 목표 피크 대비 비율로 화면에서 나눈다(표시용). 목표를 넘은 칸은 경고색이다.
- 성적표용으로 가짜 데이터에 넣은 값(백엔드와 확정 필요): `summary`, `dailyPeaks[{ date, peakKw, expectedKw }]`, `heatmap[{ date, hour, peakKw }]`, `bill{ total, energyCharge, baseCharge, baseChargeOverTarget, monthEndEstimate, lastMonthTotal, byTariff[] }`, `exceeded[]`, `ess{}`, `solar{}`. 단가와 배출계수는 임시 값이다.

### 모니터링 > 통합 세부

위에서 아래로 "지금 값 → 피크와 추천 → 오늘 흐름" 순서다. (2026-11-16, KPI 카드 구성으로 변경. 이전 구성은 커밋 `7677556`에 있다)

- 1줄 KPI 5개: 공장 소비전력(공급원 비율 막대) / 한전 구매전력(목표 피크 대비 %, 넘으면 경고색) / 태양광 발전량 / ESS 충·방전("방전 500 kW", "충전 300 kW", "대기 0.0 kW"처럼 방향을 숫자 앞에 적음) / 배터리 잔량(SOC, 배터리실 온도). 왼쪽부터 "공장 소비 = 한전 + 태양광 + ESS"로 읽히는 순서다. 카드는 낮게 잡아 2줄이 첫 화면에 들어오게 한다. (2026-11-16에 4개에서 5개로 변경) 카드는 `components/KpiCards.vue`에 있고 설비 모니터링 화면도 같은 카드를 쓴다.
- 2줄: 지금 15분 구간(`PeakWindowCard.vue`) / ESS 추천(`EssAdviceCard.vue`).
  - 지금 15분 구간: 왼쪽에 예상 평균·한 줄 판정·단계, 오른쪽에 피크 게이지(정상·주의·경고 띠 위에 예상 평균 표시), 목표 피크·예상 평균·방어 필요 전력·남은 시간, 구간 진행 막대. 단계와 기준선은 백엔드가 주는 값을 쓴다. 게이지에 그리는 범위만 목표 피크 기준으로 화면에서 정한다(표시용). 주의선 기준(예: 목표의 97%)은 확인 필요.
  - ESS 추천: 행동(충전/방전/대기), 추천 kW, 이유 문장, 판단 근거(백엔드가 준 `usedValues` 목록을 그대로), `[방전 500 kW 적용]` `[넘기기]` 버튼. 기본은 **운영자 승인 모드**다. 추천 만료 규칙은 확인 필요이며, 정해지기 전에는 최신 추천 1건만 버튼을 활성화한다.
- 3줄: 오늘 전력 추이(공장 소비·한전 구매·태양광 선, 목표 피크선, 최대부하 회색 띠, "지금" 세로선. 가로축은 하루 전체이고 아직 오지 않은 시간은 비워 둔다) / 이벤트 로그(단계 변화, 추천 발생, 적용·넘김, 15분 구간 종료를 최신 순으로 10건. 단계는 도형과 색으로 표시). 공급원 흐름 카드는 2026-11-16에 이벤트 로그로 바꿨고, 공급원별 kW와 비율은 KPI의 공장 소비전력 카드에서 본다.
- 연결이 끊기면 값을 지우지 않으며, 지금 15분 구간 카드는 "통신 단절"로 바뀌고 버튼은 비활성화한다. 버튼 아래에 눌리지 않는 이유를 적는다.
- 이 화면용으로 가짜 데이터에 넣은 값(백엔드와 확정 필요): 추천의 `usedValues[{ label, value, unit }]`, 이벤트(`getRecentEvents`: `occurredAt`, `level`(`CRITICAL`·`WARNING`·`NORMAL`·`INFO`), `message`). 통신 오류와 설정 변경 이벤트는 백엔드가 기록해 줘야 해서 아직 없다.
- 이전 구성에 있던 설비 순위, 이번 달 피크, 부하 시간대 사용량, 최근 1시간 추세는 이 화면에서 뺐다. Store와 가짜 데이터의 해당 함수(`fetchRecent` 등)는 남아 있다.

### 분석 > 추이 분석 세부

기간을 골라 전력, 배터리 잔량, 온도·날씨를 같은 시간 축에 놓고 보는 화면이다.

- 조회 조건: 기간(오늘·최근 7일·이번 달·직접 입력), 간격(15분·1시간·1일), 보기 항목 6개. 조건을 바꾸면 바로 다시 조회한다(조회 버튼 없음). 조회 기간에 오늘이 들어 있으면 15분 구간이 바뀔 때마다 조용히 다시 받는다.
- 기간 요약 6개 → 왼쪽에 그래프 세 개(전력 kW / 배터리 잔량 % / 온도 ℃와 날씨) → 오른쪽에 시간대별 사용 패턴, 추천 처리별 결과, 눈에 띄는 구간.
- 단위가 다른 값은 한 그래프에 섞지 않고 세 그래프로 나눈다. 세 그래프는 같은 가로축 설정(`timeAxis`)을 쓴다. 날씨는 온도 그래프의 날짜 아래에 적는다.
- "눈에 띄는 구간"을 누르면 그 시각이 세 그래프에 세로선("선택")으로 표시된다. 다시 누르면 지워진다.
- 요약 숫자, 시간대별 평균, 처리별 결과, 눈에 띄는 구간은 **백엔드가 계산해 준 값**을 그대로 보여 준다. 화면에서는 목표 대비 %만 구한다.
- `Chart.vue`는 이전 설정에 새 설정을 덮어쓰므로, 선의 개수가 줄어드는 그래프(보기 항목을 끄는 전력 그래프)는 `:key`를 바꿔 새로 만든다.
- 이 화면용 가짜 데이터(백엔드와 확정 필요): `GET /api/analyses/trend?from=&to=&interval=` → `targetPeakKw`, `socLowLimit`, `socHighLimit`, `roomTempLimitC`, `summary{}`, `points[{ recordedAt, loadKw, gridKw, solarKw, essKw, socPercent, roomTempC, outsideTempC }]`, `weather[{ date, text }]`, `hourly[{ hour, avgGridKw, period }]`, `byStatus[{ status, count, defendedCount, defendedPercent, avgResultPeakKw }]`, `highlights[{ at, label, value, unit, level }]`. `interval`은 `QUARTER`·`HOUR`·`DAY`, `essKw`는 방전이 +, 충전이 −.

### 분석 > 피크 분석 세부

기간을 골라 피크가 언제, 얼마나 높았는지 보는 화면이다.

- 조회 조건: 기간(이번 달·지난 달·최근 7일·직접 입력). 바꾸면 바로 다시 조회한다.
- 요약 숫자 4개(기간 중 최대 피크, 목표를 넘은 구간 수, 평균 피크 저감, 피크가 잦은 시간대) → 일별 최대 피크와 저감량 → 피크가 몰리는 시간대(날짜 × 시각 히트맵) / 피크가 높았던 구간 8개(그때의 추천 처리 포함).
- 요약 숫자와 구간 순위는 **백엔드가 계산해 준 값**이다. 히트맵의 색 단계만 목표 피크 대비 비율로 화면에서 나눈다(표시용).
- 일별 그래프와 히트맵은 월간 성적표에도 있다. 가짜 백엔드는 두 화면이 같은 데이터를 쓰게 해서, 같은 달이면 최대 피크와 평균 저감 숫자가 서로 같다.
- 히트맵은 날짜 수에 맞춰 높이를 잡고, 날짜 수가 바뀌면 `:key`로 그래프를 새로 만든다.
- 이 화면용 가짜 데이터(백엔드와 확정 필요): `GET /api/analyses/peak?from=&to=` → `hasData`, `targetPeakKw`, `summary{ maxPeakKw, maxPeakAt, exceededCount, windowCount, avgReductionKw, maxReductionKw, busyFrom, busyTo, busyPeriodLabel }`, `dailyPeaks[{ date, peakKw, expectedKw }]`, `heatmap[{ date, hour, peakKw }]`, `topWindows[{ windowStart, windowEnd, peakKw, status, note }]`.
- 모든 메뉴에 화면이 생겨 `ComingSoonPage.vue`는 지금 쓰는 곳이 없다. 새 메뉴를 먼저 걸어 둘 때 쓰려고 남겨 두었다.

## 6. 반드시 지키는 규칙

### 계산은 백엔드가 한다

- 15분 피크 예측, 추천 판단, 절감액, 탄소는 **백엔드가 계산한 값을 표시만** 한다. 화면 코드에서 같은 계산을 다시 구현하지 않는다.
- 프론트에서 하는 계산은 단위 변환, 비율(%), 합계처럼 표현을 위한 것만 허용한다.

### 시각은 서버 값을 쓴다

- 시뮬레이터는 배속으로 돌 수 있다. 화면의 "현재 시각", 15분 구간, 남은 시간은 모두 API 응답의 시각 값에서 만든다.
- 가짜 백엔드(`fakeBackend.js`)는 기본 **10배속**으로 돈다(15분 구간이 1분 30초). 주소 뒤에 `?speed=1`(실제 속도)~`?speed=120`을 붙이면 바꿀 수 있고, 새로 고치면 기본값으로 돌아간다. 배속일 때는 왼쪽 메뉴의 시각 아래에 "시뮬레이션 10배속"이 보인다(`status.simulationSpeed`, 필드는 확인 필요).
- 업무 표시용으로 `Date.now()`나 `new Date()`(인자 없이)를 쓰지 않는다. 브라우저 시계는 "마지막 수신 후 경과 시간" 판단에만 쓴다.
- 백엔드 시각은 `LocalDateTime`(한국 시간, 예: `2026-11-14T14:03:00`)이다.

### 값의 출처를 구분한다

> **현재 상태 (2026-11-14):** 화면에서 출처 표시(실측·시뮬레이션·계산값·가상)를 일단 모두 뺐다. 다시 넣기로 정하기 전까지는 새 화면에도 넣지 않는다. 아래 규칙은 다시 넣을 때의 기준이다.

- 수치의 출처는 셋 중 하나다: `실측`(인버터·모터), `시뮬레이션`, `계산값`. API가 주는 구분값을 그대로 표시한다. (구분 필드는 확인 필요)
- 태양광과 ESS에는 항상 "가상" 표시를 붙인다.
- 금액과 탄소에는 항상 "추정" 표시를 붙인다. "절감했다"가 아니라 "절감 추정"으로 쓴다. "ESS를 쓰면 무조건 이익"이라는 식의 문구는 쓰지 않는다.

### 공급원 비율

- 설비별 한전/태양광/ESS 비율은 색 + 글자 + 막대를 함께 써서 표시한다.
- 비율 계산 방식은 확인 필요다. 비율은 API가 주는 값을 그대로 그리고, 프론트에서 임의로 만들지 않는다(고정 비율 가정 금지).

### 실시간 갱신 (폴링)

- 방식은 폴링으로 확정이다. 기본 주기는 5초(시뮬레이터 주기와 같음)이며, 최종 주기는 확인 필요.
- 페이지의 `onMounted`에서 `setInterval`로 Store의 조회 함수를 부르고, `onBeforeUnmount`에서 반드시 `clearInterval` 한다.
- 최신 상태·추천(`fetchLatest`)은 헤더가 모든 화면에서 쓰므로 `MainLayout.vue`에서 한 번만 폴링한다. 각 페이지는 그 화면에만 필요한 데이터만 따로 받는다.
- 요청이 연속으로 실패하면 연결 표시등을 "연결 안 됨"으로 바꾸고, 마지막 수신값과 수신 시각을 유지해 보여 준다. 값을 0이나 빈칸으로 바꾸지 않는다.
- 값이 없을 때는 `—`로 표시한다. 0과 "값 없음"을 구분한다.

## 7. API 연동

- 흐름: 페이지 → Store(`use{기능}Store.js`) → API 함수(`{기능}Api.js`) → `api()`. 페이지에서 `fetch`를 직접 부르지 않는다.
- 필드 이름은 **Swagger(http://localhost:8080/swagger-ui.html)에 나온 그대로** 쓴다. 이름을 바꾸는 변환 코드를 두지 않는다.
- 주소 규칙은 `/api/{복수형 명사}`다. `api()`에는 `/api`를 뺀 경로를 넘긴다. (예: `api('/battery-statuses/latest')`)
- **백엔드가 아직 없는 API**는 해당 `{기능}Api.js` 함수가 임시로 가짜 데이터를 돌려주게 만든다. 함수 이름과 응답 모양은 실제와 같게 하고, `// TODO: 백엔드 연결 후 교체` 주석을 남긴다. Store와 페이지는 고치지 않아도 되게 한다.
- 현재 백엔드에는 API가 하나도 없다. 아래는 기획 초안이며 백엔드와 확정되면 `api/` 폴더만 고친다.

| 메서드 | 주소 | 용도 |
|---|---|---|
| GET | `/api/battery-statuses/latest` | 실시간 관제용 최신 1건 |
| GET | `/api/battery-statuses?from=&to=` | 그래프용 기간 조회 |
| GET | `/api/battery-decisions?from=&to=` | 운영 이력 |
| PATCH | `/api/battery-decisions/{id}` | 적용 / 무시 |
| GET | `/api/reports?month=` | 성적표 |
| GET | `/api/energy-settings` | 설정 조회 |
| PUT | `/api/energy-settings/{key}` | 설정 변경 |

주요 값 (초안, 확인 필요):

- 상태 1건: `recordedAt`, `loadKw`, `solarKw`, `chargeKw`, `dischargeKw`, `gridKw`, `socPercent`, `windowKwh`, `predictedKw`
- 추천 1건: `decidedAt`, `ruleNo`, `action`(`CHARGE`/`DISCHARGE`/`IDLE`), `powerKw`, `reason`, `status`(`RECOMMENDED`/`APPLIED`/`IGNORED`/`AUTO`), `appliedBy`, `appliedAt`, `resultPeakKw`
- 배터리실 온도, 날씨, 값의 출처 구분, 설비별 소비전력·공급원 비율 필드는 확인 필요.
- 가짜 데이터에 임시로 넣어 쓰는 값(백엔드와 확정 필요): 15분 구간 누적 `windowPoints[{ minute, demandKw }]`, 최대 피크 `todayPeakKw`·`monthPeakKw`, 요금 시간대 `tariff{ period, label, until, nextLabel, periods[] }`, ESS `pcsStatus`·`sohPercent`.

성적표의 운영 방식 비교(한전 100% / 태양광 자가소비 / 태양광+ESS 추천 운영)는 **지금 성적표 화면에 넣지 않는다** (2026-11-15 결정). 나중에 백엔드의 가상 시나리오 시뮬레이션이 연결되면 그때 비교 화면을 만든다. 만들 때는 개수를 코드에 박지 않고 API가 주는 배열을 `v-for`로 그대로 그린다.

## 8. 코드 규칙

- 컴포넌트 순서는 `<script setup>` → `<template>` → `<style scoped>`.
- `defineProps`에는 타입과 기본값을 적는다. 이벤트는 `defineEmits`로 선언한다.
- Store는 `const xxxStore = useXxxStore()`로 가져와 `xxxStore.값`으로 쓴다. 구조 분해하지 않는다.
- API 오류는 `try-catch`로 잡아 `error.message`를 화면에 보여 준다.
- 숫자·단위 표시는 `utils/format.js`의 함수로만 한다. 템플릿에서 `toFixed`나 문자열 더하기로 단위를 붙이지 않는다.
  - kW: 100 미만은 소수 1자리, 그 이상은 정수. 천 단위 구분 기호 사용.
  - kWh 소수 1자리, % 소수 1자리, 원은 정수, 탄소는 kg 또는 t.
- 주석과 화면 문구는 한국어로 쓴다. "SCADA"라는 명칭은 화면에 쓰지 않는다.
- 같은 것은 어느 화면에서나 같은 말로 부른다. 추천을 받아들이지 않는 것은 "넘기기"(버튼) / "넘김"(기록)이고 "무시"라고 쓰지 않는다. 다른 화면으로 가는 링크는 도착하는 화면 이름을 그대로 쓴다(예: "추천 이력 보기").
- 요청받은 범위만 고친다. 관련 없는 파일을 정리하거나 이름을 바꾸지 않는다.

```css
  --bg: #eef0f2;  --card: #fff;  --line: #dde1e5;  --line-strong: #b9c0c7;
  --ink: #14181c; --ink-2: #3c444c; --mute: #646e77;  --faint: #98a1a9;
  --ok: #2f7d4f;  --warn: #9c5f08; --crit: #c8372d; --lost: #8a9299;
  --accent: #14181c; /* 강조색을 따로 두지 않고 먹색을 쓴다. 색은 상태와 공급원에만 쓴다 */
  /* 공급원 색: 임시값, 팀 확정 필요 */
  --src-grid: #5b6472;  --src-solar: #d19a00;  --src-ess: #0f8f8a;
}
```

- 색을 코드에 직접 쓰지 않고 변수를 쓴다. (ECharts `option`에는 CSS 변수를 못 쓰므로 같은 값을 적고 주석으로 변수 이름을 남긴다)
- 상태는 색만으로 구분하지 않는다. 항상 도형과 글자를 함께 쓴다: `● 정상` `▲ 주의` `■ 경고` `◆ 통신 단절`.
- 상태색(초록·주황·빨강·회색)을 공급원이나 차트 계열 색으로 재사용하지 않는다.
- 공급원은 색과 함께 이름(한전/태양광/ESS)을 항상 글자로 적는다.
- 숫자에는 `font-variant-numeric: tabular-nums`를 적용한다.
- 기준 해상도는 1920×1080이다. 실시간 관제 화면의 지표, 피크 게이지, 추천 카드는 스크롤 없이 첫 화면에 들어와야 한다. 1366×768에서도 깨지지 않게 한다.
- `reset.css`가 브라우저 기본 스타일을 모두 지운 상태다. `h1`, `button` 등도 필요한 스타일을 직접 지정한다.

## 10. 차트 (ECharts)

- 차트는 `<Chart :option="option" :height="300" />`로만 그린다. 생성·크기 조절·정리는 `Chart.vue`가 한다. 페이지에서 `echarts.init`을 직접 부르지 않는다.
- 백엔드 데이터로 그릴 때는 `computed`로 `option`을 만든다.
- `option`에 `animation: false`를 넣는다. 값이 계속 갱신되는 화면이라 깜빡임이 생긴다.
- `Chart.vue`는 화면에 나타나는 순간 차트를 만든다. 크기가 0이면 오류가 나므로, 탭 전환처럼 숨기는 경우 `v-show` 대신 `v-if`를 쓴다.
- 선 그래프 축은 하나만 쓴다. kW와 %처럼 단위가 다른 값은 그래프를 나눈다.
- 툴팁은 항상 넣고, 계열이 2개 이상이면 범례를 넣는다.

### 공장 레이아웃 (평면만, 3D는 범위 밖)

- `components/FactoryLayoutMap.vue`에서 `.vue` 템플릿에 SVG를 직접 그리고 `@click`으로 설비 선택을 처리한다. (ECharts 지도는 쓰지 않는다)
- 설비 위치는 컴포넌트 안의 `EQUIPMENT_BOXES`에 있고, `id`는 API의 `equipments[].id`와 같아야 한다.

#### 공장 컨셉

현대위아 창원1공장의 열관리 시스템(TMS) 라인을 모델로 한 **가상의 전기차 열관리 부품 공장**이다.
생산 품목(냉각수 허브 모듈, HVAC, 쿨링모듈, 열교환기)만 공개 자료 기준이고, **공정·설비·전력 값은 임시로 정한 추정**이다. 화면에는 회사 이름을 쓰지 않고 "열관리 부품 공장 (가상)"으로 적는다.

| 구역 | 공정 | 설비 (ID) |
|---|---|---|
| Z1 열교환기 가공 | 핀·튜브 성형, 코어 조립 | 핀 성형기 `Z1-FIN`, 튜브 가공기 `Z1-TUBE`, 코어 조립기 `Z1-CORE` |
| Z2 브레이징 | 알루미늄 코어 접합 | 브레이징로 `Z2-FURN`(전기식 가정, 가장 큰 부하), 탈지·건조기 `Z2-DRY` |
| Z3 사출 | HVAC 케이스 성형 | 사출기 `Z3-INJ1` `Z3-INJ2`, 금형 온조기 `Z3-TEMP` |
| Z4 모듈 조립 | 모듈 조립 | 1번 모터 `Z4-MOTOR1`(조립 라인 컨베이어, 실측), 체결 로봇 `Z4-ROBOT` |
| Z5 검사 | 기밀·성능 검사 | 기밀 검사기 `Z5-LEAK`, 성능 시험기 `Z5-EOL` |
| 유틸리티동 | 공장 공통 | 공기압축기 `U-COMP`, 냉각 칠러 `U-CHIL`, 공조·조명 `U-HVAC` |

- 공정 흐름: Z1 → Z2 → (Z3 부품과 함께) Z4 → Z5 → 출하.
- 피크 이야기: 브레이징로 승온과 사출기 가동이 같은 15분 구간에 겹치면 피크가 오른다.
- 전기실(수전설비·배전반), ESS실(PCS + 배터리 랙), 옥상 태양광을 함께 그린다.
- 설비 목록과 ID는 백엔드와 확정 전이다(확인 필요).

## 12. 작업 방식

- 화면을 만들거나 고치면 `npm run dev`로 직접 열어 확인하고, 1920×1080과 1366×768에서 깨지지 않는지 본다. 콘솔 오류가 없어야 끝난 것이다.
- 다음 상태를 모두 확인한다: 정상, 피크 초과 예상, 값 없음, 서버 연결 끊김(백엔드를 끈 상태), 목록이 빈 경우.
- 작업이 끝나면 무엇을, 왜 바꿨는지 초보자도 이해할 수 있게 설명한다.
- 커밋은 요청받았을 때만 한다. 브랜치·커밋 규칙은 `AGENTS.md`와 `docs/4-collaboration-guide.md`를 따른다. (`main` 직접 커밋 금지, `타입: 설명`, AI 작성 표시 금지)
