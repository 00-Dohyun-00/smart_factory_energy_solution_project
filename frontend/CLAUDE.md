# WATTever 프론트엔드 — CLAUDE.md

프론트엔드(`frontend/`) 작업에만 적용한다.

- 공통 규칙(폴더, 파일 이름, 금지 사항, 커밋)은 루트의 `AGENTS.md`가 기준이다. 이 문서와 다르면 **`AGENTS.md`를 따른다.**
- 코드 예제는 `docs/3-frontend-guide.md`, 기획 원문은 루트의 `WATTever_회의내용정리.md`, 팀 결정은 `docs/decisions.md`를 본다.
- `확인 필요` 표시는 팀에서 아직 정하지 않은 항목이다. 해당 항목에 걸리는 작업은 임의로 정하지 말고 먼저 질문한다.

## 1. 프로젝트 한 줄 요약

공장에 한전 전기 + 태양광 + ESS(배터리)를 함께 공급한다고 가정하고, **15분 최대수요전력(피크) 방어를 최우선**으로 ESS의 충전/방전/대기를 추천해 전기요금을 줄이는 모니터링·운영 추천 시스템이다. 비싼 요금 시간대의 ESS 활용은 차순위 옵션이다.
태양광과 ESS는 가상 설비이고, 데이터는 대부분 시뮬레이션이다. (시연에서는 1번 모터의 실제 값을 일부 결합할 수 있다)

## 2. 기술 스택

| 항목 | 결정 |
|---|---|
| 프레임워크 | Vue 3, Composition API, `<script setup>` |
| 언어 | JavaScript (TypeScript 쓰지 않음) |
| 빌드 | Vite |
| 라우팅 / 상태 | Vue Router / Pinia |
| 차트 | ECharts — 공통 컴포넌트 `@/components/Chart.vue`로만 사용 |
| UI | 라이브러리 없이 직접 작성 (`<style scoped>` + 색 변수) |
| HTTP | `@/api/client.js`의 `api()` 함수 |
| 검사 / 정렬 | oxlint / Prettier |
| 패키지 매니저 | npm |

- Element Plus, vue-echarts, Tailwind 등 `package.json`에 없는 라이브러리는 쓰지 않는다. 필요하면 설치하지 말고 이유와 대안을 먼저 제안한다.
- 수정 금지 공통 파일: `package.json`, `vite.config.js`, `src/api/client.js`, `src/components/Chart.vue`, `src/styles/reset.css`. 꼭 고쳐야 하면 이유를 설명하고 먼저 확인받는다.

## 3. 명령어

```bash
npm install
npm run dev        # http://localhost:5173 (/api 요청은 백엔드 :8080으로 전달됨)
npm run format     # Prettier 자동 정렬
npm run lint       # oxlint
npm run build
```

작업이 끝나면 `npm run format && npm run lint && npm run build`가 통과해야 한다.
환경 변수 파일(`.env`)은 프론트엔드에서 쓰지 않는다.

## 4. 폴더 구조

```
src/
  api/
    client.js          # 공통 호출 함수 api() (수정 금지)
    {기능}Api.js        # 기능별 API 함수 (예: batteryStatusApi.js)
  stores/              # Pinia. use{기능}Store.js
  pages/               # 화면 단위 (주소 1개 = 파일 1개), XxxPage.vue
  components/          # 재사용 UI. Chart.vue(수정 금지), 상태 표시, 지표 카드 등
  layouts/             # MainLayout.vue (헤더 + RouterView)
  router/index.js      # 페이지 목록
  styles/              # reset.css(수정 금지), global.css(색 변수·전체 공통 스타일)
  utils/format.js      # 숫자·단위 표시 함수 (필요해질 때 만든다)
  assets/              # 이미지, factory-layout.svg 등
```

- import는 항상 `@/` 경로, `.vue`는 확장자까지 쓴다.
- 새 폴더나 공통 유틸은 꼭 필요할 때만 만든다. 초보자가 읽을 수 있는 단순한 코드가 우선이다.

## 5. 화면

메뉴는 다섯 개(모니터링 · 분석 · 보고서 · 운영 로그 · 환경 설정)이고, 메뉴 아래에 하위 화면을 둔다. 화면은 한 번에 하나씩 만들어 추가한다. (2026-11-15 결정)

| 메뉴 | 하위 화면 | 경로 | 파일 | 상태 |
|---|---|---|---|---|
| 모니터링 | 통합 | `/` | `MonitoringPage.vue` | 있음 |
| 모니터링 | 설비 모니터링 | `/monitoring/diagram` | `PowerDiagramPage.vue` | 있음 |
| 분석 | 추이 분석 | `/analysis/trend` | `TrendAnalysisPage.vue` | 있음 |
| 분석 | 피크 분석 | `/analysis/peak` | `PeakAnalysisPage.vue` | 있음 |
| 보고서 | 월간 성적표 | `/report` | `ReportPage.vue` | 있음 |
| 운영 로그 | 추천 이력 | `/logs` | `HistoryPage.vue` | 있음 (`/history`로 들어와도 열림) |
| 환경 설정 | 기준값 | `/settings` | `SettingsPage.vue` | 있음 |

- 왼쪽 메뉴(`MainLayout.vue`): 맨 위 `WATTever`, 자동 모드일 때 "자동 모드 · 시뮬레이션" 표시, 접었다 펴는 메뉴 4개, 맨 아래 환경 설정 링크와 현재 시각·날씨·서버 연결 표시. 환경 설정은 자주 쓰지 않아 메뉴 목록(`menus`)에서 빼고 맨 아래에 따로 둔다(2026-11-17, UI 피드백). "통합" 옆에는 지금 피크 단계(■ 경고, ▲ 주의)를 표시한다. 위쪽 헤더는 없다.
- 맨 위 줄 세 개 버튼으로 왼쪽 메뉴 전체를 접었다 편다. 접으면 좁은 띠(56px)만 남고, 띠에는 자동 모드("자동"), 피크 단계, 연결 상태만 보인다. 접은 상태는 브라우저 저장소(`localStorage`)에 적어 두어 새로 고쳐도 유지된다.
- 서버 연결이 끊겼다는 알림은 `MainLayout.vue`가 모든 화면 위쪽에 한 번만 띄운다(마지막 수신 시각, 자동 재연결 안내, `[지금 다시 시도]`). 각 화면에서 따로 만들지 않는다.
- 서버는 응답하는데 새 1분 기록이 3분 넘게 안 들어오면(시뮬레이터를 켠 백엔드가 꺼진 경우) 같은 자리에 주의 알림("▲ 새 기록이 N분째 들어오지 않습니다")을 띄우고, 왼쪽 시계 아래에도 "▲ 기록이 N분째 멈춤"을 적는다(2026-11-19). 멈춘 시간은 서버 시각(`windowEnd − remainingSeconds`)과 `recordedAt`의 차이다(`useRealtimeStore.dataStoppedMinutes`). 연결이 끊기면 연결 끊김 알림만 보인다.
- `routes`의 `meta`에 `parent`(메뉴 이름)와 `title`(화면 이름)을 적는다. `title`은 브라우저 탭 제목(`통합 · WATTever`)에 쓰인다. 없는 주소는 왼쪽 메뉴가 보이는 채로 404 안내를 보여 준다.
- 다른 화면으로 옮기면 본문 스크롤을 맨 위로 올린다.
- 새 화면을 만들면 `router/index.js`의 `routes`와 `MainLayout.vue`의 `menus` 두 곳에 추가한다. 아직 없는 화면은 `ComingSoonPage.vue`를 연결하고 `meta`에 메뉴 이름과 제목을 적는다.
- 화면마다 맨 위에 "메뉴 › 화면 이름" 제목 줄을 둔다(`global.css`의 `.crumb`).
- **화면을 새로 만들거나 구성을 크게 바꿀 때는 Figma 시안을 먼저 그려 확인받고 코드로 옮긴다.** 시안 파일: https://www.figma.com/design/T3ZjEgHClEAQC999RJqbMX ("실시간 관제 시안 2" 페이지 아래쪽에 메뉴별 화면이 있다)
- 공장 레이아웃(평면도)은 쓰지 않기로 했다. 설비는 설비 모니터링 화면과 "지금 많이 쓰는 설비" 순위로 보여 준다.
- 회의록의 예시값(공장 2,570kW, 목표 1,800kW 등)은 UI 예시일 뿐 실제 값이 아니다.

### 운영 로그 > 추천 이력 세부

메뉴 이름은 "운영 로그"다(2026-11-16에 "로그"에서 변경). 주소(`/logs`)와 파일 이름(`HistoryPage.vue`)은 그대로 두었다.

- 표 한 줄 = 추천 1건. 열: 추천 시각, 대상 시간, 추천(행동·kW), 규칙, 예상 피크, 처리(추천 중/적용/자동/넘김), 처리자, 처리 시각, 실제 피크, 목표 달성(달성/초과). (2026-11-17, UI 피드백으로 칼럼 이름을 바꾸고 처리자와 처리 시각을 나눔. 예전 이름: 15분 구간, 근거, 예상 평균, 처리자·시각, 결과 피크, 결과. 조회 조건의 "근거"는 "규칙"으로 바꿈. 펼친 줄은 "이유"와 "판단 근거" 제목으로 나눔)
- 줄을 누르면 추천 이유와 판단에 쓴 값(`usedValues`)이 펼쳐진다. 판단 값 목록은 백엔드가 주는 배열을 그대로 그린다.
- 기간(오늘/최근 7일/직접 입력)은 API로 조회하고, 추천·처리·근거·검색어 조건은 받아 온 목록을 화면에서 거른다. 근거 선택 상자의 목록은 받아 온 이력에 나온 `ruleLabel`로 만든다.
- "오늘"은 서버가 보낸 시각(`status.recordedAt`)에서 구한다. 조회 기간에 오늘이 들어 있으면 5초마다 조용히 다시 받는다.
- 이 화면에서는 적용/넘기기를 하지 않는다(읽기 전용). 처리는 모니터링 > 통합에서 한다.
- 자동으로 처리한 기록은 실제 제어가 아니므로 처리자를 "자동 모드 (시뮬레이션)"으로, 처리 조건을 "자동 (시뮬레이션)"으로 적는다.
- 이력용으로 가짜 데이터에 넣은 값(백엔드와 확정 필요): `windowStart`, `windowEnd`, `ruleLabel`, `predictedKw`, `resultPeakKw`, `resultStatus`(`DEFENDED`/`EXCEEDED`).

### 성적표 세부

- 주제는 "한 달 동안 ESS 추천 운영이 실제로 어땠나"이다. 달은 ◀ ▶로 고르고, 이번 달은 오늘까지의 값만 보여 준다. "이번 달"은 서버 시각에서 구한다.
- 구성(2026-11-17, UI 피드백으로 세로 배치로 변경): 위에서 아래로 한 줄씩 핵심 숫자 4개(피크 방어 성공률, 최대 피크, 평균 피크 저감량, 전기요금 추정) → 전기요금 카드(`BillCard.vue`) → 일별 최대 피크와 저감량(예상 막대 위에 실제 막대를 겹침) → 피크 시간대 히트맵(날짜 × 시각) → 목표를 넘은 구간 표 → ESS 운용 → 태양광·탄소. 화면 폭은 최대 1,200px로 가운데에 둔다.
- 전기요금 카드는 통신비 청구서처럼 "이 달 금액 → 비교 막대 → 요금 내역" 순서다. 비교는 이 달(진행 중이면 월말 예상) / 전달(`lastMonthTotal`) / 작년 같은 달이다. 작년 같은 달 금액은 성적표 API를 1년 전 달로 한 번 더 불러 `bill.total`을 쓴다(`useReportStore.lastYearTotal`, 실패하거나 기록이 없으면 "—"·"기록 없음"). 요금 내역은 기본요금(최대 피크 기준)과 시간대별 전력량요금, 합계 줄이다.
- 제목 줄의 `[인쇄 · PDF 저장]`은 브라우저 인쇄 창을 연다(`window.print()`, 라이브러리 없음). 인쇄할 때는 왼쪽 메뉴와 버튼을 숨기고 A4 세로에 맞게 줄인다(`global.css`와 `MainLayout.vue`의 `@media print`). 인쇄할 때 그래프 캔버스는 종이 폭에 맞춰 줄이는데, ECharts가 캔버스를 여러 장 겹쳐 그리는 그래프(히트맵)는 첫 장만 흐름에 두고 나머지는 겹쳐 둔다(전부 흐름에 두면 층이 흩어짐). A4 세로 2쪽으로 찍히는 것을 헤드리스 Chrome PDF로 확인했다(2026-11-18).
- `[CSV 저장]`은 뺐다(2026-11-18, UI 피드백: 원천 데이터를 CSV로 받을 일이 적고, 받는다면 그 달 보고서를 엑셀로 받는 게 맞음). 엑셀 저장은 백엔드가 .xlsx를 만들어 주는 방식(예: `GET /api/reports/{month}/excel`)으로 팀과 맞출 예정이며, 프론트는 라이브러리를 추가하지 않는다.
- 추정값이라는 주의 문구는 화면 맨 아래에 둔다.
- 금액은 백엔드가 원 단위로 주고, 화면에서 만원 단위로 바꿔 보여 준다(`formatManwon`). 요금·저감량·탄소는 모두 추정값이라고 제목 줄에 적는다.
- 피크 저감량은 "방전하지 않았을 때의 예상 피크 − 실제 피크"이고, 두 값 모두 백엔드가 준다.
- 히트맵의 색 단계는 목표 피크 대비 비율로 화면에서 나눈다(표시용). 목표를 넘은 칸은 경고색이다.
- 성적표용으로 가짜 데이터에 넣은 값(백엔드와 확정 필요): `summary`, `dailyPeaks[{ date, peakKw, expectedKw }]`, `heatmap[{ date, hour, peakKw }]`, `bill{ total, energyCharge, baseCharge, baseChargeOverTarget, monthEndEstimate, lastMonthTotal, byTariff[] }`, `exceeded[]`, `ess{}`, `solar{}`. 단가와 배출계수는 임시 값이다.

### 모니터링 > 통합 세부

위에서 아래로 "지금 값 → 피크와 추천 → 오늘 흐름" 순서다. (2026-11-16, KPI 카드 구성으로 변경. 이전 구성은 커밋 `7677556`에 있다)

- 제목 줄 오른쪽: 자동 모드이면 먹색 띠로 "운영 모드: 자동 (시뮬레이션)"을 크게 표시한다(2026-11-17, UI 피드백).
- 1줄 KPI 5개: 공장 소비전력 / 한전 구매전력(목표 피크 대비 %, 넘으면 경고색) / 태양광 발전량 / ESS 충·방전("방전 500 kW", "충전 300 kW", "대기 0.0 kW"처럼 방향을 숫자 앞에 적음) / 배터리 잔량(SOC, 배터리실 온도). 왼쪽부터 "공장 소비 = 한전 + 태양광 + ESS"로 읽히는 순서다. (2026-11-16에 4개에서 5개로 변경) 카드는 `components/KpiCards.vue`에 있다. (설비 모니터링 화면에서도 썼으나 2026-11-18에 뺐다)
  - 카드마다 숫자 위에 반원 계기판(바늘)을 그린다. 멀리서도 보이게 하기 위해서다(2026-11-17, UI 피드백. 이전 막대 모양은 커밋 `c560e9c`에 있다). SVG를 직접 그리며 ECharts는 쓰지 않는다.
  - 눈금 범위는 표시용으로 화면에서 정한다: 공장 소비 0~목표 피크×1.5(공급원 비율대로 색을 나눠 칠함), 한전 구매 0~목표 피크×1.2(정상·주의·경고 띠, 기준선은 백엔드의 `warnKw`·`targetPeakKw`), 태양광은 공장 소비 대비 비율, ESS는 가운데가 대기이고 왼쪽 충전·오른쪽 방전(끝은 설정의 최대 출력), 배터리 잔량 0~100%(설정의 하한·상한 밖은 연한 띠).
- 2줄: 예상 피크(`PeakWindowCard.vue`) / ESS 추천(`EssAdviceCard.vue`).
  - 예상 피크(2026-11-18, UI 피드백으로 제목을 "현재 15분 피크 구간"에서 바꾸고 가로 막대 게이지를 15분 흐름 그래프로 바꿈. 이전 막대 모양은 커밋 `dd472f1`에 있다): 제목 오른쪽에 구간과 남은 시간(`14:00 – 14:15 / 남은 6분 0초`). 왼쪽에 단계 표시(테두리만 둔 작은 표시), 예상 피크(큰 숫자), 목표 피크·현재 누적·추가 방전. 오른쪽에 15분 흐름 그래프: 가로축은 구간 15분, 실선은 지금까지 쌓인 값(명세 1번 `windowPoints[{ minute, demandKw }]`, 0에서 시작해 15분 끝의 값이 그 구간의 피크), 점선은 지금 점에서 구간 끝의 예상 피크까지, 목표 피크선, 아직 오지 않은 시간은 옅은 띠. "현재 누적"은 `windowPoints`의 마지막 값이다. 세로축 끝만 목표·예상 중 큰 값 기준으로 화면에서 정한다(표시용). 주의선 기준(예: 목표의 97%)은 확인 필요.
  - ESS 추천(2026-11-18 개편): 무엇을(행동·추천 kW·끝나는 시각 `~ 22:30`) → 하면 무엇이 좋은지(백엔드가 보낸 한두 문장 `reason`, 예: "적용하면 이번 15분 평균이 1,846 → 1,720 kW로 목표(1,800 kW) 안에 들어옵니다. 넘기면 …") → `[방전 500 kW 적용]` `[넘기기]`. 기본은 **운영자 승인 모드**다. 추천 만료 규칙은 확인 필요이며, 정해지기 전에는 최신 추천 1건만 버튼을 활성화한다.
    - 이번 15분 상황은 예상 피크 카드, 배터리 잔량은 KPI 카드가 이미 보여 주므로 이 카드에 다시 그리지 않는다. 판단 근거 목록(`usedValues`)은 카드에서 뺐고 추천 이력 화면에서 본다.
    - 문장 속 "지금대로면" 값은 예상 피크 카드의 예상 피크와 같은 계산이다. (전에는 가짜 백엔드가 상태를 만드는 중에 기다리는(await) 사이 추천 조회가 먼저 끝나, 추천 카드가 한 번 전 값을 보여 줬음 → 수정)
    - 처리 상태는 지난 일이 아니라 지금 상태로 적는다: 적용 중(시각·처리자) / 자동 적용 중 / 넘김. 적용 중이면 추천 kW는 지금 실제로 내는 출력이다. (전에는 "적용했습니다"가 추천이 유지되는 동안 계속 남아 지난 일처럼 보였음)
  - 예상 피크 카드의 단계 표시 옆 판정 문장("목표 N kW 아래" 등)은 단계 표시와 뜻이 겹쳐 뺐다(2026-11-18). 첫 값을 받기 전에는 "○ 불러오는 중", 연결이 끊기면 "◆ 통신 단절"(숫자와 그래프도 회색)이다. 멈춘 시각은 화면 위 연결 끊김 알림과 KPI 카드에 나온다. 1600px 이하에서는 왼쪽 칸과 숫자를 줄인다.
- 3줄: 오늘 그래프 두 개를 위아래로 둔다. 위는 "오늘 공장 소비"(공장 소비 선, 태양광 점선), 아래는 "오늘 한전 구매"(한전 구매 선, 목표 피크선). 한 그래프에 선이 많으면 비교가 어려워 나눴다(2026-11-17, UI 피드백). 두 그래프 모두 최대부하 회색 띠와 "지금" 세로선이 있고, 가로축은 하루 전체이며 아직 오지 않은 시간은 비워 둔다 / 이벤트 로그(단계 변화, 추천 발생, 적용·넘김, 15분 구간 종료를 최신 순으로 10건. 단계는 도형과 색으로 표시). 공급원 흐름 카드는 2026-11-16에 이벤트 로그로 바꿨고, 공급원별 kW와 비율은 KPI의 공장 소비전력 카드에서 본다.
- 연결이 끊기면 값을 지우지 않으며, 예상 피크 카드는 "통신 단절"로 바뀌고 버튼은 비활성화한다. 버튼 아래에 눌리지 않는 이유를 적는다.
- 이 화면용으로 가짜 데이터에 넣은 값(백엔드와 확정 필요): 추천의 `usedValues[{ label, value, unit }]`(추천 이력용), 추천의 `reason`(하면 무엇이 좋은지, 5초마다 새로 계산), 이벤트(`getRecentEvents`: `occurredAt`, `level`(`CRITICAL`·`WARNING`·`NORMAL`·`INFO`), `message`). 통신 오류와 설정 변경 이벤트는 백엔드가 기록해 줘야 해서 아직 없다.
- 이전 구성에 있던 설비 순위, 이번 달 피크, 부하 시간대 사용량, 최근 1시간 추세는 이 화면에서 뺐다. Store와 가짜 데이터의 해당 함수(`fetchRecent` 등)는 남아 있다.

### 분석 > 추이 분석 세부

기간을 골라 전력, 배터리 잔량, 온도·날씨를 같은 시간 축에 놓고 보는 화면이다.

- 조회 조건: 기간(오늘·최근 7일·이번 달·직접 입력), 간격(15분·1시간·1일), 보기 항목 6개. 조건을 바꾸면 바로 다시 조회한다(조회 버튼 없음). 조회 기간에 오늘이 들어 있으면 15분 구간이 바뀔 때마다 조용히 다시 받는다.
- 기간 요약 6개 → 왼쪽에 그래프 세 개(전력 kW / 배터리 잔량 % / 온도 ℃와 날씨) → 오른쪽에 시간대별 사용 패턴, 추천 처리별 결과, 눈에 띄는 구간.
- 전력 그래프가 이 화면의 주인공이라 크게(높이 460, 전체 화면에서 보는 것을 기준으로 함), 배터리 잔량(100)·온도와 날씨(120)는 보조라 작게 그리고 제목도 작게 한다(2026-11-18, UI 피드백). 세 그래프는 위아래로 두어 가로축을 맞춘다. 온도 그래프는 낮아서 범례를 왼쪽 위에 둔다(오른쪽 위의 "온도 제한" 글자와 겹치지 않게).
- 단위가 다른 값은 한 그래프에 섞지 않고 세 그래프로 나눈다. 세 그래프는 같은 가로축 설정(`timeAxis`)을 쓴다. 날씨는 온도 그래프의 날짜 아래에 적는다.
- 가로축은 조회 기간의 모든 칸(시작일 0시 ~ 종료일 끝, 간격만큼)으로 만든다(`fillSlots`). 백엔드는 기록이 있는 칸만 주므로, 받은 칸만 그리면 기록 없는 날(시뮬레이터가 꺼져 있던 날)이 사라지고 앞뒤 날짜가 붙어 보였다. 기록 없는 칸은 값을 비워 선이 끊기고, 툴팁에 "기록 없음"이 나온다. 시간대별 사용 패턴 막대도 같다(2026-11-19).
- "눈에 띄는 구간"을 누르면 그 시각이 세 그래프에 세로선("선택")으로 표시된다. 다시 누르면 지워진다.
- 추천 핀(2026-11-17, UI 피드백): 같은 기간의 추천 이력(`getBatteryDecisions`, 추천 이력 화면과 같은 API · `useHistoryStore`)을 받아, 전력 그래프 위쪽 띠에 추천이 나온 칸마다 처리 상태 기호(● 적용 · ◇ 자동 · ✕ 넘김 · ○ 추천 중)만 적고, 툴팁 아래에 그 칸의 추천(시각·행동·kW·처리)을 최대 4건 보여 준다. 세로선은 추천이 많아 그래프가 지저분해져서 긋지 않고, 배터리 잔량·온도 그래프에는 표시하지 않는다. 전력 그래프 제목 줄의 `추천 표시` 체크로 끌 수 있다. 이력을 못 받으면 그래프는 그대로 두고 전력 그래프 위에 안내만 띄운다.
- 시간대별 사용 패턴은 `[시간 순]`(막대 그래프)과 `[순위]`(한전 구매가 많은 시각 10개)로 바꿔 본다. 순위는 백엔드가 준 `hourly`를 정렬만 한 것이고, 막대 길이는 1위를 100%로 본 표시용 비율이다.
- 요약 숫자, 시간대별 평균, 처리별 결과, 눈에 띄는 구간은 **백엔드가 계산해 준 값**을 그대로 보여 준다. 화면에서는 목표 대비 %만 구한다.
- `Chart.vue`는 이전 설정에 새 설정을 덮어쓰므로, 선의 개수가 줄어드는 그래프(보기 항목을 끄는 전력 그래프)는 `:key`를 바꿔 새로 만든다.
- 이 화면용 가짜 데이터(백엔드와 확정 필요): `GET /api/analyses/trend?from=&to=&interval=` → `targetPeakKw`, `socLowLimit`, `socHighLimit`, `roomTempLimitC`, `summary{}`, `points[{ recordedAt, loadKw, gridKw, solarKw, essKw, socPercent, roomTempC, outsideTempC }]`, `weather[{ date, text }]`, `hourly[{ hour, avgGridKw, period }]`, `byStatus[{ status, count, defendedCount, defendedPercent, avgResultPeakKw }]`, `highlights[{ at, label, value, unit, level }]`. `interval`은 `QUARTER`·`HOUR`·`DAY`, `essKw`는 방전이 +, 충전이 −.

### 분석 > 피크 분석 세부

기간을 골라 피크가 언제, 얼마나 높았는지 보는 화면이다.

- 조회 조건: 기간(이번 달·지난 달·최근 7일·직접 입력). 바꾸면 바로 다시 조회한다.
- 요약 숫자 4개(기간 중 최대 피크, 목표를 넘은 구간 수, 평균 피크 저감, 피크가 잦은 시간대) → 일별 최대 피크와 저감량 → 피크가 몰리는 시간대(날짜 × 시각 히트맵) / 피크가 높았던 구간 8개(그때의 추천 처리 포함).
- UI 피드백 반영(2026-11-17):
  - 목표를 넘은 구간 카드: 횟수 옆에 전체 15분 구간 대비 비율을 괄호로 붙인다(`exceededCount ÷ windowCount`, 표시용 비율).
  - 히트맵: "피크가 높았던 구간" 표의 줄을 누르면 그 날 그 시각 칸에 굵은 테두리와 "11-02 08:30 · 1,841 kW" 이름표를 단다. 다시 누르거나 기간을 바꾸면 지워진다.
  - 테두리는 ECharts `custom` 시리즈로 칸 크기를 재서 그린다. `markArea`는 칸 가운데에 맞춰져 반 칸씩 밀려서 쓰지 않는다. `visualMap`은 `seriesIndex: 0`으로 히트맵에만 적용한다.
- 요약 숫자와 구간 순위는 **백엔드가 계산해 준 값**이다. 히트맵의 색 단계만 목표 피크 대비 비율로 화면에서 나눈다(표시용).
- 일별 그래프와 히트맵은 조회 기간(`from`~`to`)의 모든 날짜로 칸을 만든다(`fillDays`). 기록 없는 날은 막대·칸 없이 빈자리로 남는다. 월간 성적표의 일별 그래프·히트맵·ESS 일별 방전량도 같은 방식이다(`periodStart`~`periodEnd`)(2026-11-19).
- 일별 그래프와 히트맵은 월간 성적표에도 있다. 가짜 백엔드는 두 화면이 같은 데이터를 쓰게 해서, 같은 달이면 최대 피크와 평균 저감 숫자가 서로 같다.
- 히트맵은 날짜 수에 맞춰 높이를 잡고, 날짜 수가 바뀌면 `:key`로 그래프를 새로 만든다.
- 이 화면용 가짜 데이터(백엔드와 확정 필요): `GET /api/analyses/peak?from=&to=` → `hasData`, `targetPeakKw`, `summary{ maxPeakKw, maxPeakAt, exceededCount, windowCount, avgReductionKw, maxReductionKw, busyFrom, busyTo, busyPeriodLabel }`, `dailyPeaks[{ date, peakKw, expectedKw }]`, `heatmap[{ date, hour, peakKw }]`, `topWindows[{ windowStart, windowEnd, peakKw, status, note }]`.
- 모든 메뉴에 화면이 생겨 `ComingSoonPage.vue`는 지금 쓰는 곳이 없다. 새 메뉴를 먼저 걸어 둘 때 쓰려고 남겨 두었다.

### 환경 설정 > 기준값 세부

- 묶음 세 개(피크 / ESS / 운영)를 나란히 두고 **묶음마다 저장**한다. 항목 목록(`GROUPS`)은 화면에 있고, `key`는 백엔드 설정 이름과 같아야 한다.
- 요금 단가 4개(경부하·중간부하·최대부하·기본요금)와 충·방전 효율은 화면에서 뺐다(2026-11-17, UI 피드백). 단가는 요금 기준표에서, 효율은 외부에서 받아오는 값이라 여기서 고치지 않는다. 예전 변경 기록에 이 항목이 있으면 이름이 보이도록 `RETIRED_FIELDS`에 이름과 단위만 남겨 두었다. 백엔드 설정과 가짜 백엔드의 값은 그대로다.
- 바꿨지만 저장하지 않은 값은 왼쪽 굵은 줄과 "저장 전 값 → 바꾼 값"으로 표시한다. `[되돌리기]`는 그 묶음을 저장된 값으로 돌린다.
- 저장하지 않은 값이 있으면 다른 화면으로 갈 때 "저장하지 않은 값이 N건 있습니다…"라고 묻는다(`onBeforeRouteLeave` + `window.confirm`). 새로 고침·탭 닫기 때는 `beforeunload`로 브라우저가 묻는다. 이동을 취소하면 탭 제목도 바뀌지 않는다(`router.afterEach`의 `failure` 확인).
- 빈칸이나 범위를 벗어난 값은 화면에서 먼저 알려 주고 저장 버튼을 막는다. 값이 올바른지는 백엔드도 확인하며, 저장에 실패하면 받은 메시지를 묶음 아래에 보여 준다.
- 아래의 변경 기록은 백엔드가 준 목록(저장 시각, 항목, 저장 전·후 값, 변경자)을 그대로 보여 준다.
- 설정은 `useSettingsStore`에 있고 공통 틀(`MainLayout.vue`)이 처음에 한 번 받아 둔다. "화면 갱신 주기"는 공통 틀의 폴링 주기로 쓰이고, 운영 모드가 자동이면 왼쪽 메뉴 맨 위, 통합 화면 제목 줄, ESS 추천 카드에 자동 모드(시뮬레이션)임을 표시한다.
- 가짜 백엔드에서는 저장한 값이 바로 반영된다: 목표 피크·주의선(통합의 단계와 게이지), 최대 출력(추천 kW), 배터리 용량·잔량 하한/상한·온도 제한(분석), 운영 모드(자동이면 추천을 바로 적용한 것으로 기록). 추천 유효 시간은 저장만 되고 계산에는 쓰이지 않는다. 새로 고치면 처음 값으로 돌아간다.
- 명세 v0.2 모양(2026-11-17): `GET /api/settings` → `[{ key, group, label, value(문자열), unit, updatedAt, updatedBy }]`, `PUT /api/settings`(본문 `[{ key, value }]`, 묶음의 바뀐 값을 한 번에), `GET /api/setting-histories?from=&to=` → `[{ id, changedAt, key, label, oldValue, newValue, changedBy }]`(서버 날짜 기준 최근 30일). 화면의 설정 키: `peak.target_kw`, `peak.warn_ratio`, `ess.capacity_kwh`·`ess.max_power_kw`(명세 "보기만" → 읽기 전용), `ess.soc_low`, `ess.soc_high`, `ess.room_temp_limit`, `operation.auto_mode`(`"true"`/`"false"`). `operation.poll_seconds`, `operation.decision_valid_minutes`는 명세에 없어 화면에서 뺄지 팀 결정 대기.

### 모니터링 > 설비 모니터링 세부

화면 이름은 "설비 모니터링"이다(2026-11-16에 "계통도"에서 변경). 주소(`/monitoring/diagram`)와 파일 이름(`PowerDiagramPage.vue`, `PowerTree.vue`)은 그대로 두었다. 화면 안의 그림은 "전력 계통"이라고 부른다.

- 맨 위의 KPI 5개(`KpiCards.vue`)는 뺐다(2026-11-18, UI 피드백: 통합 화면과 겹치고, 이 화면은 설비가 주인공이어야 함). 그 자리에 설비 전체 통계를 넣을 예정이며 구성은 팀 검토 중이다.
- 위에서 아래로: 공급원 3곳(한전 수전·태양광 인버터·ESS PCS) → 주 모선 → 구역 6곳 → 고른 구역의 설비(`PowerTree.vue`, SVG 직접 그림).
- 구역을 누르면 그 구역이 선택되고 아래에 설비가 펼쳐진다. 한 번에 한 구역만 펼친다. 고른 구역은 주소에 적는다(`/monitoring/diagram?zone=Z3`).
- 오른쪽 상세: 고른 구역의 전력과 공장 대비 비율, 최근 1시간 추이, 설비별 전력, 오늘 최대·평균·사용량. 최근 1시간 그래프의 세로축은 0부터 그린다(범위를 좁히면 작은 변화가 크게 보임). 상세를 받지 못하면 `[다시 시도]`를 보여 준다.
- 공급원 상자에는 kW와 공장 대비 비율(`sourceRatio`)을 적는다. ESS는 충전 중이면 충전 전력, 그 밖에는 방전 전력을 보여 준다.
- 구역 합계와 비율은 설비 값을 더해 화면에서 구한다(표시용 합계·비율). 차단기는 그림일 뿐이고 상태 데이터나 조작은 없다.
- 이 화면용으로 가짜 데이터에 넣은 값(백엔드와 확정 필요): 구역 상세(`getZoneRecent`: `points[]`, `todayMaxKw`, `todayAvgKw`, `todayKwh`).

## 6. 반드시 지키는 규칙

### 계산은 백엔드가 한다

- 15분 피크 예측, 추천 판단, 절감액, 탄소는 **백엔드가 계산한 값을 표시만** 한다. 화면 코드에서 같은 계산을 다시 구현하지 않는다.
- 프론트에서 하는 계산은 단위 변환, 비율(%), 합계처럼 표현을 위한 것만 허용한다.

### 시각은 서버 값을 쓴다

- 시뮬레이터는 배속으로 돌 수 있다. 화면의 "현재 시각", 15분 구간, 남은 시간은 모두 API 응답의 시각 값에서 만든다.
- 2026-11-19부터 모든 화면이 실제 백엔드를 쓴다. "지금"과 "오늘"은 `site-powers/latest`의 `recordedAt`에서 구한다. `recordedAt`은 **마지막 1분 기록의 시각**이다(2026-11-19 백엔드 변경, 그 전에는 서버 시각). 그래서 시뮬레이터가 멈추면 왼쪽 메뉴 시계와 "오늘"이 마지막 기록 시각에 멈춘다. 15분 구간(`windowStart`·`windowEnd`·`remainingSeconds`)은 서버의 지금 시각 기준이다. 백엔드는 배속이 없어 `simulationSpeed`가 1이고, 그때는 배속 표시를 숨긴다. 가짜 백엔드(`fakeBackend.js`)는 더 이상 어느 화면도 부르지 않는다(예전에는 기본 10배속이라 실제 API 날짜와 어긋났음 — 이슈 #25-1).
- 업무 표시용으로 `Date.now()`나 `new Date()`(인자 없이)를 쓰지 않는다. 브라우저 시계는 "마지막 수신 후 경과 시간" 판단에만 쓴다.
- 백엔드 시각은 `LocalDateTime`(한국 시간, 예: `2026-11-14T14:03:00`)이다.

### 값의 출처를 구분한다

> **현재 상태 (2026-11-14):** 화면에서 출처 표시(실측·시뮬레이션·계산값·가상)를 일단 모두 뺐다. 다시 넣기로 정하기 전까지는 새 화면에도 넣지 않는다. 아래 규칙은 다시 넣을 때의 기준이다.

- 수치의 출처는 셋 중 하나다: `실측`(인버터·모터), `시뮬레이션`, `계산값`. API가 주는 구분값을 그대로 표시한다. (구분 필드는 확인 필요)
- 태양광과 ESS에는 항상 "가상" 표시를 붙인다.
- 금액과 탄소에는 항상 "추정" 표시를 붙인다. "절감했다"가 아니라 "절감 추정"으로 쓴다. "ESS를 쓰면 무조건 이익"이라는 식의 문구는 쓰지 않는다.

### 공급원 비율

- 설비별 한전/태양광/ESS 비율은 색 + 글자 + 막대를 함께 써서 표시한다.
- 비율 계산 방식은 확인 필요다. 비율은 API가 주는 값을 그대로 그리고, 프론트에서 임의로 만들지 않는다(고정 비율 가정 금지).

### 실시간 갱신 (폴링)

- 방식은 폴링으로 확정이다. 기본 주기는 5초(시뮬레이터 주기와 같음)이며, 최종 주기는 확인 필요.
- 페이지의 `onMounted`에서 `setInterval`로 Store의 조회 함수를 부르고, `onBeforeUnmount`에서 반드시 `clearInterval` 한다.
- 최신 상태·추천(`fetchLatest`)은 헤더가 모든 화면에서 쓰므로 `MainLayout.vue`에서 한 번만 폴링한다. 각 페이지는 그 화면에만 필요한 데이터만 따로 받는다.
- 요청이 연속으로 실패하면 연결 표시등을 "연결 안 됨"으로 바꾸고, 마지막 수신값과 수신 시각을 유지해 보여 준다. 값을 0이나 빈칸으로 바꾸지 않는다.
- 조회 화면(추이·피크 분석, 성적표)도 다시 받기에 실패하면 받아 둔 결과를 지우지 않고, 위에 공통 실패 띠(`global.css`의 `.error-band`)와 `[다시 시도]`만 띄운다. 성적표는 다른 달로 옮기다 실패하면 이전 달 숫자가 새 달처럼 보이지 않게 전체 오류로 보여 준다.
- 기간 조회 API(추이·피크 분석, 추천 이력)는 백엔드가 최대 62일까지만 받는다. 화면의 날짜 검사(`dateError`)가 62일을 넘으면 요청을 보내지 않고 "기간은 최대 62일까지 조회할 수 있습니다."를 보여 준다(2026-11-19, 이슈 #25). 주소로 들어온 기간(`/logs?from=&to=`)도 62일을 넘으면 무시하고 "오늘"로 시작한다.
- 조회 기간은 서버 시각으로 정하므로, 서버 시각을 아직 못 받았으면 "서버에서 현재 시각을 받으면 자동으로 조회합니다"를 보여 준다("이력 없음"이나 끝없는 "불러오는 중"으로 보이지 않게).
- 값이 없을 때는 `—`로 표시한다. 0과 "값 없음"을 구분한다.

## 7. API 연동

- 흐름: 페이지 → Store(`use{기능}Store.js`) → API 함수(`{기능}Api.js`) → `api()`. 페이지에서 `fetch`를 직접 부르지 않는다.
- 필드 이름은 **Swagger(http://localhost:8080/swagger-ui.html)에 나온 그대로** 쓴다. 이름을 바꾸는 변환 코드를 두지 않는다.
- 주소 규칙은 `/api/{복수형 명사}`다. `api()`에는 `/api`를 뺀 경로를 넘긴다. (예: `api('/site-powers/latest')`)
- **백엔드가 아직 없는 API**는 해당 `{기능}Api.js` 함수가 임시로 가짜 데이터를 돌려주게 만든다. 함수 이름과 응답 모양은 실제와 같게 하고, `// TODO: 백엔드 연결 후 교체` 주석을 남긴다. Store와 페이지는 고치지 않아도 되게 한다.
- 주소와 응답 모양의 기준은 **팀 API 명세 v0.2**(구글 시트 "(api 명세서) 2조 에너지솔루션")다. 명세와 화면의 차이·백엔드 요청 목록은 `docs/api-spec-diff.md`에 있다. (예전 `docs/api-spec.md`는 v0.1 주소라 쓰지 않는다)
- 명세의 API는 모두 실제 백엔드에 연결했다(2026-11-19). 아래 표의 "쓰는 화면" 칸에 연결한 날짜를 적는다. 새 API가 백엔드보다 먼저 필요하면 위 규칙대로 가짜 데이터로 시작하고, 열리면 실제로 바꾼 뒤 표에 "(연결됨)"을 적는다.

- 명세 6번(`/api/site-powers/recent`)은 쓰는 화면이 없어 함수를 지웠다.
- 명세 16번(`/api/demand-intervals`)은 백엔드가 피크 분석 응답의 `topWindows`로 함께 주기로 만들어서 함수를 지웠다(2026-11-18). `useAnalysisStore.peakWindows`는 `topWindows`를 꺼내 둔 것이다.
- 백엔드가 설정 값을 못 찾으면 분석·성적표의 `targetPeakKw` 등이 `null`로 온다. 이때 화면은 목표선·"목표 초과/달성"·히트맵 색 단계를 그리지 않는다(값을 지어내지 않음). 성적표는 `hasData`가 true여도 `dailyPeaks`·`heatmap`이 `null`일 수 있어 빈 목록으로 보고 "기록 없음"을 보여 준다.
- 설정은 공용 DB 값이라 화면에서 저장하면 팀원 모두에게 바로 바뀐다. 백엔드가 저장을 허용하는 키는 화면에서 고칠 수 있는 항목과 같다(`peak.target_kw`·`peak.warn_ratio`·`ess.soc_low`·`ess.soc_high`·`ess.room_temp_limit`·`operation.auto_mode`·`operation.poll_seconds`·`operation.decision_valid_minutes`). 배터리 용량과 최대 출력은 백엔드에서도 보기 전용이다. 실시간 화면은 아직 가짜 데이터라 저장한 목표 피크가 통합 화면의 단계·게이지에는 반영되지 않는다.
- 설정 값은 명세대로 **문자열**로 오고 간다. `useSettingsStore`가 `values`에서 숫자·`true`/`false`로 바꿔 주고, 저장할 때 다시 문자열로 보낸다. 키 이름은 명세 그대로 쓴다(예: `settingsStore.values['ess.max_power_kw']`).
- 실시간 연결하면서 맞춘 것(2026-11-19):
  - 구역 코드는 백엔드 그대로 `Z1`~`Z6`이다(유틸리티 = `Z6`, 예전 프론트는 `U`). 색 변수도 `--zone-z6`, 테마 키 `zoneZ6`.
  - 설비의 구역은 `site-powers/latest`의 `equipments[].zoneId`(값은 `Z1`~`Z6`, 한전·태양광·ESS는 `null`)를 쓴다. 백엔드가 #29 요청으로 넣어 줬다(2026-11-19). 그 전에 쓰던 `GET /api/equipment`로 구역을 붙이는 임시 코드는 지웠다.
  - 이벤트 종류는 백엔드 `eventType`(`STAGE_CHANGE`·`RECOMMEND`·`HANDLE`·`INTERVAL_END`·`COMM`·`SETTING`)을 쓴다. 백엔드는 화면용 코드 `category`(`STAGE`·`ACTION`·`WINDOW` 등)도 함께 주지만 프론트는 쓰지 않는다.
  - 날씨 기록이 없으면 `weather`가 `null`로 오고, 왼쪽 메뉴의 날씨 칸을 숨긴다.
  - 화면 갱신 주기가 짧으면(설정 `operation.poll_seconds`, 공용 DB 값) 앞 요청이 끝나기 전에는 다음 폴링을 건너뛴다.
  - [적용]/[넘기기]는 공용 DB에 바로 기록되고, 적용하면 시뮬레이터에 ESS 명령이 내려간다.

성적표의 운영 방식 비교(한전 100% / 태양광 자가소비 / 태양광+ESS 추천 운영)는 **지금 성적표 화면에 넣지 않는다** (2026-11-15 결정). 나중에 백엔드의 가상 시나리오 시뮬레이션이 연결되면 그때 비교 화면을 만든다. 만들 때는 개수를 코드에 박지 않고 API가 주는 배열을 `v-for`로 그대로 그린다.

## 8. 코드 규칙

- 컴포넌트 순서는 `<script setup>` → `<template>` → `<style scoped>`.
- `defineProps`에는 타입과 기본값을 적는다. 이벤트는 `defineEmits`로 선언한다.
- Store는 `const xxxStore = useXxxStore()`로 가져와 `xxxStore.값`으로 쓴다. 구조 분해하지 않는다.
- API 오류는 `try-catch`로 잡아 `error.message`를 화면에 보여 준다.
- 숫자·단위 표시는 `utils/format.js`의 함수로만 한다. 템플릿에서 `toFixed`나 문자열 더하기로 단위를 붙이지 않는다.
  - kW: 100 미만은 소수 1자리, 그 이상은 정수. 천 단위 구분 기호 사용.
  - kWh 소수 1자리, % 소수 1자리, 원은 정수, 탄소는 kg 또는 t.
- 주석과 화면 문구는 한국어로 쓴다. "SCADA"라는 명칭은 화면에 쓰지 않는다.
- 같은 것은 어느 화면에서나 같은 말로 부른다. 추천을 받아들이지 않는 것은 "넘기기"(버튼) / "넘김"(기록)이고 "무시"라고 쓰지 않는다. 다른 화면으로 가는 링크는 도착하는 화면 이름을 그대로 쓴다(예: "추천 이력 보기").
- 용어표 (2026-11-17 통일, 새 화면도 이 말을 쓴다):

  | 뜻 | 쓰는 말 | 쓰지 않는 말 |
  |---|---|---|
  | 15분 평균이 목표 피크를 지켰는지 | 목표 달성 / 목표 초과 (표 칸 값은 "● 달성" / "■ 초과") | 목표 이내 |
  | 구간이 끝난 뒤 실제 15분 평균 | 실제 피크 | 결과 피크 |
  | 지금 구간(또는 추천 당시) 예상한 15분 평균 | 예상 피크 | 예상 평균 |
  | 표에서 15분 구간의 시각 범위 칸 | 대상 시간 ("15분 구간 N개"처럼 개수를 셀 때는 15분 구간) | 15분 구간(칸 이름) |
  | 추천을 낸 규칙 이름 (피크 방어, 계획 방전 등) | 규칙 | 근거, 이유 |
  | 추천을 왜 냈는지 설명하는 문장 / 판단에 쓴 값 | 이유 / 판단 근거 | — |
  | 더 방전해야 하는 전력 (`defenseKw`) | 추가 방전 | 방어 필요 전력 |
  | 운영 방식 | 운영자 승인 모드 / 자동 모드 (시뮬레이션) | 운영자 승인 |
  | 처리 상태 | 추천 중 / 적용 / 자동 / 넘김 | 자동 (시뮬레이션) — 표·선택 상자에서는 "자동"만 |
  | 설비가 온도를 올리는 상태 (`HEATING`, 브레이징로) | 가열 중 (▲) | 승온 중 |
  | 성적표에서 보고 있는 달의 전 달 | 전달 (기간 버튼처럼 오늘 기준이면 "지난 달") | — |

  판단 근거 이름(`usedValues.label`)과 이유 문장은 백엔드가 글자 그대로 보내므로, 가짜 백엔드도 이 표에 맞췄고 실제 백엔드 팀과도 맞춰야 한다.
- 요청받은 범위만 고친다. 관련 없는 파일을 정리하거나 이름을 바꾸지 않는다.

## 9. 디자인

밝고 절제된 톤이다. 그림자, 그라데이션, 글로우를 쓰지 않는다. 카드는 흰 배경에 얇은 테두리만 둔다.

색 변수는 `styles/global.css`의 `:root`에 있다. 새 색이 필요하면 여기에 변수로 추가해서 쓴다.

```css
:root {
  --bg: #eef0f2;  --card: #fff;  --line: #dde1e5;  --line-strong: #b9c0c7;
  --ink: #14181c; --ink-2: #3c444c; --mute: #646e77;  --faint: #98a1a9;
  --ok: #2f7d4f;  --warn: #9c5f08; --crit: #c8372d; --lost: #8a9299;
  --accent: #14181c; /* 강조색을 따로 두지 않고 먹색을 쓴다. 색은 상태와 공급원에만 쓴다 */
  /* 공급원 색: 임시값, 팀 확정 필요 */
  --src-grid: #5b6472;  --src-solar: #d19a00;  --src-ess: #0f8f8a;
}
```

- 색을 코드에 직접 쓰지 않고 변수를 쓴다. (ECharts `option`에는 CSS 변수를 못 쓰므로 같은 값을 적고 주석으로 변수 이름을 남긴다)
- 상태는 색만으로 구분하지 않는다. 항상 도형과 글자를 함께 쓴다: `● 정상` `▲ 주의` `■ 경고` `◆ 통신 단절`.
- 상태색(초록·주황·빨강·회색)을 공급원이나 차트 계열 색으로 재사용하지 않는다.
- 공급원은 색과 함께 이름(한전/태양광/ESS)을 항상 글자로 적는다.
- 숫자에는 `font-variant-numeric: tabular-nums`를 적용한다.
- 기준 해상도는 1920×1080이다. 실시간 관제 화면의 지표, 피크 게이지, 추천 카드는 스크롤 없이 첫 화면에 들어와야 한다. 1366×768에서도 깨지지 않게 한다.
- `reset.css`가 브라우저 기본 스타일을 모두 지운 상태다. `h1`, `button` 등도 필요한 스타일을 직접 지정한다.

## 10. 차트 (ECharts)

- 차트는 `<Chart :option="option" :height="300" />`로만 그린다. 생성·크기 조절·정리는 `Chart.vue`가 한다. 페이지에서 `echarts.init`을 직접 부르지 않는다.
- 백엔드 데이터로 그릴 때는 `computed`로 `option`을 만든다.
- `option`에 `animation: false`를 넣는다. 값이 계속 갱신되는 화면이라 깜빡임이 생긴다.
- `Chart.vue`는 화면에 나타나는 순간 차트를 만든다. 크기가 0이면 오류가 나므로, 탭 전환처럼 숨기는 경우 `v-show` 대신 `v-if`를 쓴다.
- 선 그래프 축은 하나만 쓴다. kW와 %처럼 단위가 다른 값은 그래프를 나눈다.
- 툴팁은 항상 넣고, 계열이 2개 이상이면 범례를 넣는다.

### 공장 레이아웃 (평면만, 3D는 범위 밖)

- `components/FactoryLayoutMap.vue`에서 `.vue` 템플릿에 SVG를 직접 그리고 `@click`으로 설비 선택을 처리한다. (ECharts 지도는 쓰지 않는다)
- 설비 위치는 컴포넌트 안의 `EQUIPMENT_BOXES`에 있고, `id`는 API의 `equipments[].id`와 같아야 한다.

#### 공장 컨셉

현대위아 창원1공장의 열관리 시스템(TMS) 라인을 모델로 한 **가상의 전기차 열관리 부품 공장**이다.
생산 품목(냉각수 허브 모듈, HVAC, 쿨링모듈, 열교환기)만 공개 자료 기준이고, **공정·설비·전력 값은 임시로 정한 추정**이다. 화면에는 회사 이름을 쓰지 않고 "열관리 부품 공장 (가상)"으로 적는다.

| 구역 | 공정 | 설비 (ID) |
|---|---|---|
| Z1 열교환기 가공 | 핀·튜브 성형, 코어 조립 | 핀 성형기 `Z1-FIN`, 튜브 가공기 `Z1-TUBE`, 코어 조립기 `Z1-CORE` |
| Z2 브레이징 | 알루미늄 코어 접합 | 브레이징로 `Z2-FURN`(전기식 가정, 가장 큰 부하), 탈지·건조기 `Z2-DRY` |
| Z3 사출 | HVAC 케이스 성형 | 사출기 `Z3-INJ1` `Z3-INJ2`, 금형 온조기 `Z3-TEMP` |
| Z4 모듈 조립 | 모듈 조립 | 1번 모터 `Z4-MOTOR1`(조립 라인 컨베이어, 실측), 체결 로봇 `Z4-ROBOT` |
| Z5 검사 | 기밀·성능 검사 | 기밀 검사기 `Z5-LEAK`, 성능 시험기 `Z5-EOL` |
| 유틸리티동 | 공장 공통 | 공기압축기 `U-COMP`, 냉각 칠러 `U-CHIL`, 공조·조명 `U-HVAC` |

- 공정 흐름: Z1 → Z2 → (Z3 부품과 함께) Z4 → Z5 → 출하.
- 피크 이야기: 브레이징로 가열과 사출기 가동이 같은 15분 구간에 겹치면 피크가 오른다.
- 전기실(수전설비·배전반), ESS실(PCS + 배터리 랙), 옥상 태양광을 함께 그린다.
- 설비 목록과 ID는 백엔드와 확정 전이다(확인 필요).

## 12. 작업 방식

- 화면을 만들거나 고치면 `npm run dev`로 직접 열어 확인하고, 1920×1080과 1366×768에서 깨지지 않는지 본다. 콘솔 오류가 없어야 끝난 것이다.
- 다음 상태를 모두 확인한다: 정상, 피크 초과 예상, 값 없음, 서버 연결 끊김(백엔드를 끈 상태), 목록이 빈 경우.
- 작업이 끝나면 무엇을, 왜 바꿨는지 초보자도 이해할 수 있게 설명한다.
- 커밋은 요청받았을 때만 한다. 브랜치·커밋 규칙은 `AGENTS.md`와 `docs/4-collaboration-guide.md`를 따른다. (`main` 직접 커밋 금지, `타입: 설명`, AI 작성 표시 금지)
