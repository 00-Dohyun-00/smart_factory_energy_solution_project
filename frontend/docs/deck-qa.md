## 1. 배경 · 핵심 기능 (4~7쪽) — 담당: 진수현

| 질문 | 짧은 답 |
|---|---|
| 특례 폐지가 왜 중요해요? | 최대부하 시간 방전에 붙던 기본요금 추가 할인이 없어져서, 이제는 실제 15분 피크를 낮춰야만 기본요금이 줄어듦 |
| 왜 현대위아 창원1공장이에요? | 지속가능성보고서에서 전력 피크 관리를 과제로 꼽았고 태양광도 늘리는 중. 실제 공장 데이터는 공개되지 않아 가상 공장으로 시나리오를 만듦 |
| 기존 ESS 운영과 뭐가 달라요? | 정해진 시간표 대신 96구간 예측으로 매번 계획하고, 이번 15분을 따로 한 번 더 점검 |
| 1순위 · 2순위가 뭐예요? | 1순위는 15분 피크 방어(기본요금), 2순위는 그 안에서 전력량요금 줄이기 |

## 2. 시스템 설계 (9~14쪽) — 담당: 서원준 · 한상원 · 이도현

| 질문 | 짧은 답 |
|---|---|
| 실측 장비는 뭐고 어디에 써요? | 인버터 + 모터 1대(LS iG5A). Node-RED가 Modbus로 읽어 1,000 kW 규모로 환산하고 태양광 실측 자리에 넣음(시연 전용) |
| 모터 인버터 값을 왜 태양광으로 써요? | 실제 태양광 설비가 없어서 "수집 → 저장 → 화면" 흐름을 실측값으로 보여 주려고. 한계로 인정하는 게 좋음 |
| 통신이 끊기면요? | Node-RED가 30초간 정상 데이터를 못 받으면 측정값을 `null`로 저장해 정상 값과 구분 |
| DB가 죽으면요? | 10초마다 상태 확인, 3번 연속 실패하면 로컬 백업 DB로 전환. 평소 5분마다 동기화, 복구되면 되돌림 |
| 1초 원본이 하루 86,400줄인데 괜찮아요? | 화면은 1분 집계만 조회. 응답 1초 캐시와 SQL 집계로 조회량도 줄임 |
| 1분 집계 테이블을 왜 따로 둬요? | 1초 원본을 그대로 조회하면 너무 많아서, 화면 · 분석은 1분 평균 · 최대 · 최소를 씀 |
| ERD 관계를 설명해 주세요 | 설비 1 : 전력 기록 N, 구역 1 : 설비 N, 추천 1 : 이벤트 N, 설정 1 : 변경 이력 N (13쪽) |
| 보안은요? | DB 접속 정보는 `.env`에만 두고 Git에서 뺌. 로그인은 이번 범위 밖 |
| 시뮬레이터를 여러 명이 켜면요? | 공용 DB라 중복 저장됨. `.env`의 `SIMULATOR_ENABLED=true`인 한 명만 실행 |

## 4. ESS 추천 로직 (29~30쪽) — 담당: 진수현

| 질문 | 짧은 답 |
|---|---|
| "최적화 계산"이 뭐예요? | 96칸 × 배터리 잔량 단계로 가장 싼 경로를 찾는 동적계획법. 모든 칸에서 한전 구매 ≤ 방어선, 잔량 20~90%, 최대 500 kW, 하루 끝 잔량 50% 조건을 지킴 |
| 무엇을 최소로 해요? | 전기요금 + 배터리 마모(방전 1 kWh당 20원) + 예비 잔량 부족 벌점 |
| 1분마다 다시 계산하면 추천이 들쭉날쭉하지 않아요? | 같은 15분 동안은 피크 방어를 유지. 방전이 50 kW 이상 더 필요할 때만 다시 추천하고, 풀 때는 54 kW 여유를 둠 |
| "최근 1시간 예측 오차 반영"은 어떻게 해요? | 최근 1시간 동안의 "실제 − 예측" 평균을 앞으로의 예측에 더함 |
| 잔량이 부족하면요? | "안전 제한"으로 대기 추천 |
| 추천 kW와 예상 피크 카드 값이 왜 달라요? | 추천은 최근 4분 평균을 쓰고 안전 여유를 둠. 최대 출력과 잔량으로도 자름 |

> ⚠ "최근 1시간 예측 오차"를 앞으로 24시간 전체에 더해서, 부하가 잠깐 튀면 방어선이 올라가는 문제가 있다. 시뮬레이션에서 이 부분만 고치면 ESS 몫 순 절감이 연 1,417만 → 약 2,543만 원으로 늘었다. 질문이 나오면 **개선 과제**로 답한다. ([simulation/ess-saving-simulation.md](simulation/ess-saving-simulation.md) "참고")

## 5. AI 부하 예측 (31쪽) — 담당: 진수현

| 질문 | 짧은 답 |
|---|---|
| 왜 그래디언트 부스팅이에요? | 표 형태 데이터에 강하고, 데이터 양(약 2만 5천 줄)에 맞고, 피크용 상위 90% 예측도 바로 만들 수 있어서 |
| 성능은요? | 1~9월 학습 → 10~12월 검증에서 평균 오차 56.5 kW(3.6%). 하루 피크가 "AI 예측 + 200 kW" 안에 든 날 86% |
| 200 kW는 왜요? | 예측 오차를 흡수하려고 남겨 두는 여유 잔량. 나머지 14%는 15분 점검이 막음 |
| 생산계획은 진짜예요? | 더미. UCI 데이터로 요일별 표준 일정을 만들어 씀 |
| 제철소 데이터로 학습한 모델을 부품 공장에 써도 돼요? | 한계. 실제로 적용하면 그 공장의 15분 데이터와 생산계획으로 다시 학습 |
| AI 서버가 죽으면요? | 최근 1시간 평균으로 대신 씀 |
| 딥러닝은 왜 안 썼어요? | 데이터가 적고 입력이 표 형태라 그래디언트 부스팅이 더 잘 맞음. 학습도 몇 초 |
| 다른 모델과 비교했어요? | 문서에는 "LightGBM과 이 크기에서 성능이 거의 같다"만 있음. 실제 비교 여부는 진수현 님께 확인 |
