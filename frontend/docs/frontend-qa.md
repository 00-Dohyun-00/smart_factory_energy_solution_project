# 프론트엔드 예상 질문과 답

발표·코드 리뷰에서 나올 만한 질문을 정리한 문서다. 숫자와 공식은 2026-11-22 `dev` 코드와 공용 DB(읽기만 함) 기준이다.

> 답할 때 팁: "계산은 백엔드가 하고, 프론트는 받은 값을 그대로 보여 줍니다"로 시작하고, 한마디 답 → 이유 순서로 말하면 깔끔하다.
> 프론트가 직접 하는 계산은 [6. 프론트에서 직접 하는 계산](#6-프론트에서-직접-하는-계산)에 따로 모았다.
> 구조·기술 질문은 백엔드 담당이 주로 답한다. 프론트 몫은 [10. 구조 질문](#10-구조-질문-짧게)에 짧게 남겼다.

## 1. 값은 언제 바뀌나요? (갱신 주기)

### Q. 화면 값은 몇 초마다 바뀌나요? ⭐

> **한마디:** 화면은 5초마다 서버에 묻고, 백엔드 기록은 1분마다 새로 생깁니다.

| 화면 · 영역 | 언제 다시 받나 |
|---|---|
| 공통 (왼쪽 메뉴, 통합의 KPI · 예상 피크 · ESS 추천 · 이벤트 로그) | **5초마다** (환경 설정 "화면 갱신 주기", 지금 5초) |
| 통합 > 오늘 그래프 | 15분 구간이 바뀔 때 |
| 설비 모니터링 > 구역 상세 | 1분마다 (기록 시각의 "분"이 바뀔 때) |
| 추천 이력 | 5초마다 (조회 기간에 오늘이 있을 때만) |
| 추이 분석 | 15분 구간이 바뀔 때 (조회 기간에 오늘이 있을 때만) |
| 월간 성적표 | 달을 바꿀 때만 (한 달 요약이라 자동으로 다시 받지 않음) |
| 환경 설정 | 처음 한 번, 저장할 때 |

- 지난 기간만 보는 화면은 값이 바뀌지 않으므로 다시 받지 않음

### Q. 5초마다 받는데 숫자는 왜 1분에 한 번 바뀌나요?

- 백엔드가 1초 측정값을 모아 **1분 평균**으로 저장함 → 대부분 숫자가 1분 평균이라 1분에 한 번 바뀜
- 5초로 묻는 이유: 새 1분 기록이나 새 추천이 생기면 **늦어도 5초 안에** 화면에 보이게
- 예외: **공장 소비** 카드는 그 순간 값(`liveLoadKw`, 매초 바뀜)이라 5초마다 바뀜
- 왼쪽 메뉴 시계 아래 "1분마다 갱신" 문구도 이 때문

### Q. 왜 하필 5초인가요?

- 팀 결정: "시뮬레이터 1초 측정 → 1분 저장 → 15분 피크 판단, 화면 폴링 5초" (`docs/decisions.md`)
- 더 짧게 해도 값은 1분에 한 번 바뀜 → 공용 DB(Supabase) 사용량만 늘어남
- 더 길게 하면 피크 경고와 새 추천이 늦게 보임
- 환경 설정에서 1~60초로 바꿀 수 있음

### Q. 백엔드 안에서는 값이 어떤 순서로 만들어지나요?

| 언제 | 무엇을 |
|---|---|
| 매초 | 시뮬레이터가 공장 부하 1줄 재생, 적용된 추천대로 ESS 충·방전, 배터리 잔량 계산 |
| 매분 0초 | 1분 평균 저장 (공장 소비 · 태양광 · ESS · 설비별), 한전 구매 = 공장 소비 − 태양광 − ESS |
| 매분 10초 | 피크 단계 변화, 15분 구간 끝 이벤트 기록 |
| 매분 20초 | ESS 추천 다시 판단 |
| 2 · 17 · 32 · 47분 | 날씨 · 일사량 예보 받기 (Open-Meteo, 15분 칸이 바뀌고 2분 뒤) |
| 1분마다 | 설정 · 요금표 다시 읽기 (화면에서 저장하면 바로 반영) |

- 그래서 화면에는 "새 기록 → 10초 뒤 단계 이벤트 → 20초 뒤 새 추천" 순서로 나타남
- 여러 탭이 동시에 물어도 백엔드가 1초 동안 같은 답을 재사용 → DB는 한 번만 읽음

### Q. 추천은 얼마나 자주 바뀌나요?

- **1분마다** 다시 판단하고, 내용이 바뀌었을 때만 새 추천으로 저장
- 피크 방어 방전은 그 15분 구간이 끝날 때까지 유지 (방전 → 대기 → 방전으로 깜빡이지 않게)
  - 방전이 50 kW 이상 더 필요해지면 기다리지 않고 바로 새 추천
  - 방전이 필요 없어지면 여유(목표 − 주의선, 기본 54 kW)를 두고 유지를 풂
- 적용한 추천은 "적용 시각 + 추천 유효 시간(설정 15분)"과 "그 15분 구간 끝" 중 먼저 오는 때까지 ESS에 유지
- 마지막 1분 기록이 2분 넘게 없으면(시뮬레이터 멈춤) 추천하지 않음

### Q. 서버가 끊기면 언제 알 수 있나요?

- **3번 연속** 실패하면 "연결 안 됨" (5초 주기면 약 15초 뒤). 한 번 실패로 깜빡이지 않게
- 값은 0이나 빈칸으로 지우지 않음 → **마지막 값과 받은 시각**을 그대로 보여 줌
- 화면 위에 연결 끊김 알림 + `[지금 다시 시도]`, 적용 버튼은 꺼짐
- 서버는 답하는데 새 1분 기록이 **3분 넘게** 없으면 "▲ 기록이 N분째 멈춤"
  - 기록이 1분마다라 평소에도 1분 가까이 벌어져서 3분을 기준으로 둠

### Q. 탭을 안 보고 있어도 계속 요청하나요?

- 아니요. 탭이 안 보이면(`document.hidden`) 폴링을 멈추고, 다시 보이면 바로 한 번 받은 뒤 이어서 폴링
- 앞 요청이 아직 안 끝났으면 다음 폴링은 건너뜀
- 둘 다 공용 DB 사용량을 줄이려는 것

### Q. 화면의 "현재 시각"은 어디 기준인가요?

- **서버 기록 시각**(`recordedAt` = 마지막 1분 기록의 시각). 브라우저 시계는 쓰지 않음
- 그래서 시뮬레이터가 멈추면 시계도 멈춤 → 멈춘 걸 바로 알아챌 수 있음
- 15분 구간과 남은 시간은 서버의 지금 시각 기준

### Q. 바늘이 왜 천천히 움직이나요?

- 1분 값이 한 번에 툭 바뀌어서, 0.6초 동안 이전 값 → 새 값으로 옮겨 가게 함 (표시만, 이슈 #32)
- 움직임이 끝나면 받은 값 그대로

## 2. 숫자는 어떻게 나왔나요? (통합 화면, 백엔드 계산)

### Q. 예상 피크는 어떻게 계산했나요? ⭐ 가장 많이 나옴

> **한마디:** 이번 15분 중 **지나간 시간은 실제로 쓴 전력**, **남은 시간은 지금 쓰는 전력이 그대로 이어진다고 보고** 구한 15분 평균입니다.

- 공식을 물으면: **(지금까지 1분 기록의 한전 구매 합 + 지금 한전 구매 × 남은 분) ÷ 15**
  - 예: 15분 중 5분 지남, 5분 합 7,500, 지금 1,550 kW 구매 → (7,500 + 1,550 × 10) ÷ 15 = **약 1,533 kW**
  - 남은 분 = 15 − 이번 구간에 쌓인 1분 기록 수
- 그래프에서는 지금 점부터 구간 끝까지 점선으로 그림
- 코드: `backend/.../sitepower/SitePowerService.java`

### Q. 왜 이런 방식을 썼나요?

> "한전이 기본요금을 15분 평균으로 매기기 때문에 저희도 15분 평균을 예측했습니다. 이미 지난 시간은 확정값이라 실제 값을 쓰고, 남은 시간은 길어야 15분이라 지금 쓰는 전력이 이어진다고 보는 게 가장 단순하면서 빠르게 반응합니다."

1. **기준이 15분 평균이라서:** 한전 계량기는 15분 평균을 내고, 그 최댓값이 기본요금을 정함
2. **지난 시간은 확정값이라서:** 이미 쓴 전력은 바뀌지 않으니 예측할 필요가 없음
3. **남은 시간이 짧아서:** 최대 15분 앞이라 "지금 속도" 가정이 크게 틀리지 않고, 부하가 튀면 바로 반영됨
4. **설명하기 쉬워서:** 운영자가 그래프만 보고도 이해할 수 있음

- "더 정교한 방법은요?" → 24시간 계획은 AI 부하 예측으로 짜고, 이번 15분은 이 방식으로 실제 값을 보며 보정함 (역할 분담)
- "틀릴 때는요?" → 부하가 곧 떨어지면 조금 높게 나올 수 있음. 그래서 1분마다 다시 계산하고, 추천 kW는 최근 4분 평균을 써서 튀는 값에 덜 흔들리게 함

### Q. 공장 소비가 한전 + 태양광 + ESS와 딱 맞지 않아요

- 공장 소비 카드는 **그 순간 값**(매초), 한전 · 태양광 · ESS 카드는 **1분 평균**이라 조금 다를 수 있음
- 1분 평균끼리는 공장 소비 = 한전 + 태양광 + ESS 방전 (충전 중이면 한전 = 공장 소비 − 태양광 + 충전)
- 한전 구매는 0 아래로 내려가지 않음 (남는 전기를 한전에 되파는 역송은 없다고 가정)

### Q. 현재 누적은요?

- 지금까지 쌓인 한전 구매 합 ÷ 15
- 0에서 시작해 15분 끝에 닿은 값 = 그 구간의 실제 피크

### Q. 정상·주의·경고는 어떻게 나누나요?

| 조건 | 단계 |
|---|---|
| 예상 피크 > 목표 피크 | ■ 경고 |
| 예상 피크 ≥ 목표 × 주의선 % (지금 1,800 × 97% = 1,746 kW) | ▲ 주의 |
| 그 밖 | ● 정상 |

- 주의선 97%는 목표를 넘기 전에 미리 알리려는 여유 (환경 설정에서 50~100%로 바꿀 수 있음)

### Q. 추가 방전은요?

**추가 방전 = (예상 피크 − 목표 피크) × 15 ÷ 남은 분**

- 예: 남은 10분, 목표보다 50 kW 높음 → 50 × 15 ÷ 10 = **75 kW**
- 이유: 15분 평균을 50 낮추려면 "50 kW × 15분"만큼 덜 사야 함 → 남은 10분에 나눠서 뺌

### Q. 한전·태양광·ESS 비율은 어떻게 구하나요?

- 태양광 % = 공장에 쓴 태양광 ÷ 공장 소비 (소비보다 많이 발전해도 소비만큼만 셈)
- ESS % = 방전 ÷ 공장 소비
- 한전 % = 나머지
- 충전 중에는 백엔드가 ESS를 음수로 줘서, 화면에서 ESS 0% · 한전 = 100 − 태양광으로 보여 줌 (이슈 #35-1)

### Q. 배터리 잔량은 어떻게 바뀌나요?

- 시뮬레이터가 매초 계산: 잔량 변화 = (충전량 × 효율 89.5% − 방전량) ÷ 용량 1,000 kWh
- 20~90% 밖으로는 가지 않음 (하한이면 방전 멈춤, 상한이면 충전 멈춤)

## 3. ESS 추천 (백엔드가 계산)

### Q. 추천은 어떻게 정하나요?

- 1분마다 두 단계로 정함
  1. 앞으로 24시간(15분 96칸) 충·방전 계획을 짬
     - 요금 + 배터리 마모 + 예비 잔량 부족 벌점이 가장 작은 순서
     - 모든 칸에서 한전 구매 ≤ 방어선
  2. 이번 15분의 실제 전력을 보고 계획을 보정
- 붙는 규칙 이름(순서대로): 피크 방어 → 안전 제한 → 고요금 방전 → 잉여 충전 → 저요금 충전 → 조치 없음
- 코드: `backend/.../recommendation/EssPlanner.java`, `RecommendationEngine.java`

### Q. 추천 kW는 어떻게 나오나요?

- 추가 방전과 같은 방식 + 두 가지
  - 방어선보다 **조금 더 낮게** 잡음 (안전 여유)
  - 최대 출력(500 kW)과 지금 잔량으로 낼 수 있는 만큼으로 자름
- 들쭉날쭉하지 않게 **최근 4분 평균**을 씀 → 예상 피크 카드 값과 조금 다를 수 있음
- 10 kW 미만 충·방전은 추천하지 않음

### Q. 추천 kW와 실제 방전량이 왜 달라요?

- 추천 kW는 추천이 나온 순간 기준
- 적용한 뒤에는 시뮬레이터가 최대 출력 · 잔량 · 역송 금지(방전 ≤ 공장 소비 − 태양광)로 잘라서 실제 출력을 정함

## 4. 월간 성적표 (백엔드가 계산)

### Q. 피크 방어 성공률은요?

- 피크 방어 추천이 나온 15분 구간 중, 실제 피크가 목표 이하였던 구간의 비율
- 한 구간에 추천이 여러 번이어도 1회로 셈, 안 끝난 구간은 뺌

### Q. 피크 저감량은요?

- 그날 "ESS가 없었다면 샀을 15분 평균"의 최대값 − 실제 최대 피크

### Q. 전기요금 추정은요?

- 기본요금 = 이 달 최대 피크 × 기본요금 단가(8,320원/kW)
- 전력량요금 = 시간대별 사용량 × 그 시간대 단가
- 월말 예상 = 지금까지 전력량요금 ÷ 기록된 날 수 × 그 달 날 수 + 기본요금
- 금액은 모두 "추정"으로 표시 (부가세 · 기금 제외)

### Q. 탄소 절감은요?

- 태양광으로 공장이 직접 쓴 전력량 × 배출계수(설정값 0.4594 kgCO₂/kWh)

## 5. 데이터 질문

### Q. 화면의 데이터는 진짜인가요? ⭐

> **한마디:** 공장 부하는 공개 실측 데이터를 바탕으로 한 시뮬레이션이고, 태양광 · ESS는 가상 설비입니다. 날씨와 요금표는 실제 값입니다.

| 값 | 무엇으로 만드나 | 구분 |
|---|---|---|
| 공장 소비 | 시뮬레이터가 원본 부하 데이터를 1초에 1줄씩 재생 | 시뮬레이션 |
| 설비별 전력 | 공장 소비를 설비 15대에 정격 전력 비율로 나눔 | 계산값 |
| 한전 구매 | 공장 소비 − 태양광 − ESS | 계산값 |
| 태양광 | 가상 1,000 kW 설비 | 가상 설비 |
| ESS · 배터리 잔량 | 적용된 추천대로 시뮬레이터가 충·방전 | 가상 설비 |
| 날씨 · 일사량 | Open-Meteo (공장 위치 창원 부근 좌표) | 실제 |
| 요금 | 한전 산업용(을) 고압A 선택Ⅱ 요금표 | 실제 (부가세 · 기금 제외) |
| 부하 예측 | 팀 AI 모델 | 예측값 |

### Q. 공장 부하 데이터는 어디서 왔나요?

- 출처: UCI Machine Learning Repository **"Steel Industry Energy Consumption"**
  - 광양 제철소 2018년 1년치 15분 실측 (35,040줄, 한전 수집, CC BY 4.0)
- 우리 공장 크기로 바꿈: **공장 kW = 1,300 + 1.35 × (15분 kWh × 4)** → 평균 약 1,450 kW, 최대 약 2,150 kW
- AI 부하 예측 학습과 2025년 절감 시뮬레이션이 이 값을 씀
- 실시간 시뮬레이터는 11-20부터 **1초 단위 부하 데이터** 35,040줄(9시간 44분)을 반복 재생함
  - 평균 약 1,959 kW, 1,516 ~ 2,283 kW
  - 바꾼 이유: 15분 값 1줄을 1초에 재생하니 1분 만에 1,978 → 930 kW로 튐 (이슈 #32)
  - 이 1초 데이터를 만든 방법은 백엔드 담당 확인 필요 ([11. 발표 전에 확인할 것](#11-발표-전에-확인할-것))

### Q. 왜 제철소 데이터를 썼나요?

- 우리가 모델로 한 공장(전기차 열관리 부품)의 실제 전력 데이터는 구할 수 없음
- 공개 데이터 중 1년치 15분 값이 빠짐없이 있고, 한국 공장(한전 수집)이라 15분 피크 · 요금 체계가 같음
- 그래서 **오르내리는 모양만** 빌리고, 크기는 우리 공장(목표 피크 1,800 kW)에 맞춤

### Q. 설비별 값은 실측인가요?

- 아니요. 공장 소비를 설비 15대에 **정격 전력 비율**로 나눈 값 (설비마다 ±10% 흔들림, DB 뷰 `raw_equipment_load`)
- 그래서 15대 합 = 공장 소비이고, 모든 설비가 같은 모양으로 오르내림
- 설비 목록과 정격 전력(브레이징로 600 kW, 사출기 220 kW 등, 합계 2,530 kW)은 가상 공장 기준 추정

### Q. 태양광 데이터는요?

- 가상 지붕 태양광 1,000 kW
- **실시간 값**: Node-RED가 1초마다 DB(`solar_power`)에 넣는 값을 시뮬레이터가 그대로 씀
- **ESS 계획용 예측**: Open-Meteo 15분 일사량 예보 × 1,000 kW × 성능비 0.8 ÷ 1,000
  - 성능비 0.8: 먼지 · 온도 · 변환 손실을 빼고 실제로 나오는 비율
  - 15분 예보 사이는 직선으로 이어서 계단처럼 뛰지 않게 함
- ⚠ 11-20 19:36 이후 `solar_power`에 새 값이 없어서, **11-21부터 1분 기록의 태양광이 하루 종일 0 kW**임 ([11. 발표 전에 확인할 것](#11-발표-전에-확인할-것))

### Q. ESS 값은요?

- 가상 ESS: 용량 1,000 kWh, 최대 출력 500 kW, 잔량 20~90%, 효율 89.5% (공용 DB 설정값)
- 실제 설비를 제어하지 않음. 시뮬레이터가 "지금 적용된 추천"을 읽어 매초 충·방전하고 잔량을 계산함

### Q. 요금표는요?

- 한전 **산업용(을) 고압A 선택Ⅱ** (계절 × 시간대 17줄, `tariff_period`)
- 기본요금 8,320원/kW. 부가세 · 전력산업기반기금은 넣지 않아 "추정"으로 표시

### Q. 부하 예측 AI는 뭘 썼나요?

- 모델: scikit-learn `HistGradientBoostingRegressor` (그래디언트 부스팅, LightGBM과 같은 방식)
- 입력: 생산계획 부하, 시간대, 요일, 공휴일, 어제 · 지난주 같은 시간 부하, 최근 4주 평균
- 학습 · 검증: 1~9월로 학습 → 10~12월 예측, 평균 오차 **56.5 kW (3.6%)**
- 모델 2개
  - 평균 예측 → 요금 계산용
  - 상위 90% 예측 → 피크 판단용 (평균 예측은 피크를 낮게 보는 경향)
- 생산계획은 **더미**: UCI에 없어서 1~9월 데이터로 요일 · 시간별 표준 일정을 만들어 씀
- AI 서버가 응답하지 않으면 최근 1시간 평균으로 대신 씀
- 자세한 내용: `ai/forecast/README.md`

### Q. 데이터는 얼마나 쌓였나요? (2026-11-22 19:55 기준)

- 1분 기록 약 **53.7만 줄** (2025-11-01 ~ 2026-11-22, 376일)
- 추천 266건
- 날씨(Open-Meteo) 약 1.6만 줄 (2025-01-01부터)
- 공용 DB는 팀 1명(`SIMULATOR_ENABLED=true`)만 시뮬레이터를 돌려 쌓음 (여러 명이 돌리면 중복 저장)

### Q. 시간은 실제 시간인가요? 배속은요?

- 실제 시각 그대로 흐름 (배속 없음, `simulationSpeed` = 1)
- 다만 공장 부하 데이터가 9시간 44분마다 한 바퀴라, "낮에 높고 밤에 낮은" 실제 하루 흐름과는 맞지 않음 (이슈 #32에 남은 과제로 적음)

### Q. 슬라이드마다 목표 피크가 1,500 / 1,800으로 다른데요?

- 피크 대응 장면(19~22쪽)은 시연용 가짜 백엔드라 목표 1,500 kW
- 추이 분석부터(23쪽~)는 실제 백엔드 공용 DB 값이라 목표 1,800 kW

### Q. 시연 영상은 실제 데이터인가요?

- 개발 서버에서만 켜지는 **가짜 백엔드 모드**(`?fake`)로 찍음 → 피크가 튀는 장면을 일부러 만들 수 있음
- 빌드 결과물에는 들어가지 않음

### Q. 절감 시뮬레이션(연 약 1,417만 원)은 어떤 데이터로 했나요?

- 2025년 1년, 15분 35,040칸
- 공용 DB의 2025년 날씨 · 요금표 · 설정 + UCI 부하(2018년 → 2025년 같은 달 · 같은 요일에 맞춤) + 팀 AI 예측
- 추천은 실제 백엔드 판단 엔진 코드를 그대로 불러서 계산
- 자세한 내용: [simulation/ess-saving-simulation.md](simulation/ess-saving-simulation.md)

## 7. 화면 세부

### Q. 0이랑 "값 없음"은 어떻게 구분하나요?

- 값이 없으면 `—`, 0이면 `0.0`
- 예: 설비 값이 비었을 때 그대로 더하면 0 kW로 보여서 → 구역 합계를 `—`로 둠

### Q. 상태 표시는 색으로만 하나요?

- 아니요. 색약인 사람도 구분하게 **도형 + 글자**를 같이 씀: `● 정상` `▲ 주의` `■ 경고` `◆ 통신 단절`

### Q. 설정을 여러 사람이 동시에 바꾸면요?

- 공용 DB라서 **바꾼 칸만** 저장
- 내가 손대지 않은 칸은 다른 사람이 바꾼 새 값으로 바뀜
- 저장 안 한 값이 있으면 다른 화면으로 갈 때 확인 창

### Q. 해상도는요?

- 1920×1080 기준, 1366×768에서도 깨지지 않는지 확인

## 9. "어려웠던 점" 사례

- **1분 기록이라 값이 툭 튐** → 바늘·숫자가 0.6초 동안 새 값으로 옮겨 가게 함 (이슈 #32)

## 10. 구조 질문 (짧게)

백엔드 구조 · DB · 시뮬레이터 질문은 백엔드 담당이 답한다. 프론트 몫은 이 정도다.

- **무엇으로 만들었나:** Vue 3(`<script setup>`), Vite, Pinia, Vue Router, ECharts **딱 4개**. UI 라이브러리 없이 직접 만듦 (웹이 처음인 팀이라 라이브러리를 늘리지 않음)
- **데이터 흐름:** 화면(`pages/`) → Pinia 스토어(`stores/`) → `{기능}Api.js` → `client.js`의 `api()`. 서버 주소와 오류 처리를 한 곳에 모음
- **Pinia를 쓴 이유:** 실시간 값과 설정은 여러 화면이 같이 씀 → 공통 틀(`MainLayout.vue`)이 한 번만 받아 스토어에 두고 화면은 꺼내 쓰기만 함
- **차트:** ECharts를 공통 컴포넌트 `Chart.vue` 하나로만 씀. 값이 계속 바뀌어 깜빡이지 않게 애니메이션을 끔
- **WebSocket은?** 백엔드 기록이 1분 단위라 폴링으로 충분하고 구현이 단순함
